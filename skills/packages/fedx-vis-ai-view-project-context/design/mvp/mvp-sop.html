MVP-SOP · 四输入还原大屏

前提：环境中只有 large-screen-builder skill（骨架 skeleton + 工作流 workflows + 物料库 specs + 模块索引 module-index）——没有物料站源仓库、没有平台。

0 · 输入与环境

输入是什么在流程中的作用
PM inputs需求描述：主题、指标口径、数据来源、联动期望决定「放什么」——区块清单、数据契约、interactions 联动设计
大屏设计稿整屏视觉稿（截图 / 设计文件导出）决定「放哪里」——canvas 尺寸、sections 布局（x/y/w/h）、视觉风格映射
设计素材图标、图片、装饰元素等资产文件决定「长什么样」——物料的图片类 props / 背景资源；新物料可参考
模块 spec具体模块的规格说明（Props 表 / 交互行为）决定「怎么配」——匹配或新写物料时的 props 填写依据

环境侧唯一资产 = skill 自带：skeleton/（工程骨架）、workflows/（schema-mode / big-screen-assembly / material-extract）、specs/<模块>/（spec + data-model + code + examples）、module-index.md（分类索引）。

1 · 结论先行

能还原，且这是 skill 的设计目标场景。 但能力边界由「物料匹配度」决定，分三档：

  • 全匹配 每个区块都能在 specs 里找到对应 type → 直接产 schema 出屏，零新代码
  • 部分匹配 多数区块匹配、少数缺料 → 匹配区走 schema，缺料区参照模块 spec 现写组件（skill 的建组件能力），注册后同样进 schema
  • 系统性缺口 整类能力缺失（如全新交互形态）→ 现写 + material-extract 提料回流（zip → import:material → 升级 skill），本次先占位交付

2 · SOP 主流程

1
初始化工程 workflows/schema-mode.md

复制 skill 的 skeleton/ 为宿主项目 → pnpm install。得到干净工程壳：路由 + SchemaScreen + 空 registry + renderer IIFE 产物。

2
读图与拆屏（PM inputs × 设计稿）

从设计稿提取 canvas（尺寸/缩放/背景）+ 区块栅格（每块的 x/y/w/h、标题、视觉风格）；从 PM inputs 提取每块的数据语义（指标、维度、单位）与联动关系。产出一张「区块清单」：id / 位置 / 语义 / 联动。

3
物料匹配 module-index.md + specs/

逐区块查 module-index（按 category 缩小范围）→ 命中候选后读其 spec.md 对照模块 spec 输入与设计稿视觉，验证三点：props 表达能力够不够、data-model 契约对不对、events/subscribe 支不支持期望联动。

匹配结果三类：直接可用 / 近似可用（props 定制可收敛视觉差异）/ 缺料。

4
接入匹配物料 schema-mode.md 步骤 3~4

每命中一个 type：从 specs/<模块>/code/ 拷组件进宿主 src/components/materials/<type>/（依赖与静态资源一并拷）→ 在 src/components/materials/registry.tsx 注册一行。设计素材中属于该物料的图片，按 spec 的资源路径约定落位。

5
缺料扩展（两条分支，见 §3）
6
产出 Schema big-screen-assembly.md

按区块清单逐条写 schema：canvas ← 设计稿尺寸；sections ← 每块的 type/layout/props（props 填法对照 spec Props 表与模块 spec 输入）/frame；data ← PM inputs 的数据契约（inline mock 或 url 指向宿主接口）；interactions ← 联动关系（events 派发 ↔ subscribe 订阅）。

「加屏 = 建 src/screens/<name>/ 声明 schemaUrl + App 挂 Route」，放 schema 文件即出屏。

7
验证与收敛

浏览器跑屏：区块渲染 / 数据绑定 / 联动闭环 / console 零 error。视觉对照设计稿微调 layout 与 props（只动 schema，不动物料代码——改物料会漂移 propsContract）。

8
提料回流（可选但推荐）material-extract.md

本次现写的新组件若具备复用价值 → scripts/export-material.mjs 打包 zip → 下载回物料站 → pnpm import:material（三门槛 + 人工 review）→ export:skill 发新版。skill 越用越厚，下次同类需求直接全匹配。

3 · 缺料时的两条扩展分支

分支 A · 工程内现写 本次交付优先

参照模块 spec 与设计稿视觉，在宿主 src/components/materials/<新type>/ 现写组件（React + 仓库技术栈，遵守 spec 声明的 Props / 事件契约）→ registry 注册 → 进 schema。设计素材在此消费（图标、贴图）。

适用：临时性、项目特有的区块；或时间紧先出屏。

分支 B · 标准件沉淀 长期复用

按 material-extract.md 规范把现写组件提炼为四件套（manifest 含 runtime 块 / spec / data-model / code / examples 自包含 mock）→ 打包回流物料站 → 发布新版 skill。物料的 propsContract / dataContract 即后续 AI 使用它的契约。

适用：通用性强的区块（如新的图表形态、业务卡片）。

4 · 边界与纪律（不可逾越）

  • schema 里不现写 tsx——组件只能来自 specs/ 拷贝或宿主 materials/ 现写后注册，schema 只做装配描述
  • 不改骨架副本里的物料实现——视觉差异用 props 收敛；确实不够表达 → 走分支 B 改物料站原件再回流
  • 物料间零耦合——模块之间禁止相互 import；联动只通过 interactions（events/subscribe）
  • 数据请求归宿主——物料不发起请求，schema data 契约（url/inline）由宿主环境满足
