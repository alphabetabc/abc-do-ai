### 阶段 3 · 多版本对比

对冻结清单中的每个高频组件：

- [ ] 提取 2~3 个历史版本源码
- [ ] 差异标注表：说清哪些是「活的」（可填项）、哪些是「死的」（骨架/SDK/命名）

验收：每类组件差异表完成，可回溯原始文件。

### 阶段 4 · 逐组件蒸馏

按组件逐个跑一轮（T5→T10），**做完一个交付一个，不攒批**：

- [ ] 抽骨架 + 标可填充项 → `docs/materials/<模块名>/code/`
- [ ] 固化死规则（库引用/SDK/结构/命名，AI 不可改）
- [ ] `data-model.md`（入参/出参/维度/指标，字段类型必填齐全）
- [ ] `spec.md` 交互清单（事件/触发条件/影响范围）
- [ ] `examples/` 带 mock 可渲染

验收：提示词 2.3 一致性校验全过（spec/data-model/code 三者一致）；新增模块必须带 `manifest.json`。

### 阶段 5 · 闭环验证

- [ ] 图片 + 自然语言 → 组件代码，一次成功 Demo（首阶段仅 1~2 种核心组件）
- [ ] 大屏布局的自然语言解析
- [ ] 验证反馈回填模板与规范（迭代对象是模板，不是推翻规范体系）

## 节奏

- **每日**：上午主体工作 → 下午挂共享库 → 下班前台账更新
- **每周**：周一锁本周组件清单 → 周三模板互审 → 周五闭环验证一轮

## 卡点纪律

1. 阶段 2 不冻结清单 → 不进阶段 4（防发散）
2. 阶段 4 只做「蒸馏」不做「优化重构」——骨架/SDK/命名锁死
3. 每个组件交付前必须过一致性校验（`docs/materials/_templates/prompts.md` 提示词 2.3）
4. 质量门槛命令：`pnpm build`（含 tsc -b）；本地验证 `pnpm dev:preview`
