## 1. 需求原文

> 2、4、5G 基站、机房经纬度重叠时，生成一个新的图标，点击后周边呈现所有的设备。

拆解关键点：

| # | 描述 | 关键概念 |
|---|---|---|
| ① | 设备类型 = 2G/4G/5G 基站 + 机房 | neType ∈ `{201, 3201, 8104, 10005*, 1000501–1000505}` |
| ② | 「经纬度重叠」 | 同一坐标 / 同一像素点 / 容差范围内多个设备 |
| ③ | 「生成一个新的图标」 | 用一个聚合标记代替多个独立点 |
| ④ | 「点击后周边呈现所有的设备」 | 点击聚合图 → 弹出 / 周边展示设备列表 |

### 2.2 现状与缺口

| 维度 | 现状 | 缺口 |
|---|---|---|
| **聚合触发** | `VectorLayer` 内部按 OL 默认策略聚合（看上去是基于距离，**没有明确阈值**） | 没有针对「跨图层 (基站+机房) 按经纬度合并」的逻辑 |
| **聚合对象** | 同一个图层内聚合 | 需求是「**基站 + 机房跨图层**」聚合 |
| **图标** | 单一图层样式，无「聚合标记」样式 | 没有专门的「N 个设备聚合」图标 |
| **聚合点 Tooltip** | `ElTooltipCircle` 只展示单个 siteName + 经纬度 | 没有「聚合列表」展示（多设备名 + 设备类型 + 详情入口） |
| **聚合点 Click** | `onCircleClick` → `pointClick(point)` 只透传单点 | 没有「周边呈现所有设备」的弹层 / 列表 / 联动 |
| **机房与基站合并判定** | 没有 | 缺「同一 (lon, lat) 容差内」判定函数 |

> 现有 `VectorLayer.onShowCircle` 的 `pointArr` 结构：来自 OL 内部聚合产物，**业务层无法干预** — 不能用来做「跨图层合并」。

## 3. 方案设计

### 3.1 总体思路

**在业务层（`Gis` 组件）做「跨图层合并 + 聚合标记渲染」，fedx-gis 只负责最终绘制。**

```
┌──────────────────────────────────────────────────────────────────────┐
│ 现有数据层                                                           │
│  dataStationPointsAll (neType: 201/3201/8104/900/2011)              │
│  dataMachineryRoomPointsAll (neType: 10005/1000501~1000505)         │
└──────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 新增：buildAggregatedPoints(station, machineryRoom, options)         │
│   • 扁平化所有点位（neType ∈ {201,3201,8104,10005*}）                │
│   • 按经纬度容差（默认 0.00005° ≈ 5m）分组                          │
│   • 单点：保留原样                                                   │
│   • 多点：合成一个聚合点（保留 children + 设备数量）                  │
└──────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 渲染                                                                 │
│  • VectorLayer 新图层 layerAggregatePoints（zIndex=1004，最上层）   │
│    → 单点：原样式；聚合点：专用图标 + count                           │
│  • 点击聚合点 → 打开「设备列表弹层」 ElAggregateTooltip / 新组件    │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 关键决策点

| 决策点 | 推荐 | 理由 |
|---|---|---|
| **聚合对象** | 仅 `{2G, 4G, 5G 基站 + 机房}` | 需求原文只列了这两类。BRAS/OLT/传输/应急/光缆 不参与聚合 |
| **判定粒度** | 经纬度容差（默认 `5e-5` 度 ≈ 5m，可配置） | 设备共站址通常 < 10m；后端用 WGS84，前端无需投影 |
| **聚合后图层** | 新建 `layerAggregatePoints` (zIndex 1004) | 不动现有 6 个 VectorLayer，**最小化改动** |
| **单点 vs 聚合点** | 单点不替换原图层；只把「≥2 个共点」提走 | 单点用户仍可在原图层 hover/click，行为零变化 |
| **图标** | 新增 `aggregate.png` (静态资源)；右上角角标显示设备数 | 与现有 event-* 系列图片风格一致（位于 `tab-content-1/images/`） |
| **列表展示** | 复用 `ElTooltipCircle` 的容器机制（`toolTipWindowCircle*`），新增 `ElAggregateTooltip` 组件 | 不引入新 tooltip 框架；`source` 传聚合点对象即可 |
| **点击列表项 → 右屏派发** | 复用现有 `pointClick(point)` | 列表项点 = 单点 click 的子集，逻辑完全一致 |
| **范围** | **同时改 tab1（日常）+ tab2（突发）** | 两个 Gis 都用 `getEmergencyNormalGisStationPointsApi` + `getEmergencyNormalGisMachineryRoomPointsApi`，数据源一致 |
| **Tab 隔离** | 不抽公共组件 | 按 SKILL.md 约定，两个 Tab 各自实现，新增文件分别落在 `tab-content-1/` 与 `tab-content-2/` |

### 3.3 聚合判定算法

> ⚠️ **方案更新（2026-07-13）：用户选择使用 `public/static/images/emergency-support/map/group-point.png` 作为聚合图标。**
>
> 该图标不在 fedx-gis 内置聚合机制中（fedx-gis 内部用 `gongzhan{level}.png`），因此**不能依赖 OL `createBubbleStyle`**，改为**业务层自实现聚合**：
> - 业务层用网格桶算法对基站+机房点位做合并
> - 输出**已聚合**的点喂给新图层（`isGongZhanByType: false`）
> - `pointStyle.imgUrl` 指向 `group-point.png`
> - 角标通过业务层自绘 CSS 实现

#### 网格桶聚合算法（业务层自实现）

**为什么不用 fedx-gis 内部 OL 聚合**：
- `group-point.png` 不是 OL 内部支持的气泡样式
- OL `createBubbleStyle` 强制使用 `gongzhan{level}.png`
- 自定义图标必须脱离 OL 自动聚合 → 业务层自己合并

**为什么用网格桶**：
- 3 万点 × O(n²) 配对 → 9 亿次比较 → 浏览器卡死
- 网格桶复杂度 O(n)，3 万点 < 50ms
- 无需引入新依赖（rbush）

```ts
// 网格大小：≈ 100m，比容差大一个数量级
const AGGREGATE_GRID_SIZE = 1e-3;
const AGGREGATE_TOLERANCE = 5e-5; // 5m，可配置

function buildAggregatedPoints(stationFlat: Point[], roomFlat: Point[]) {
    const all = [...stationFlat, ...roomFlat];

    // 1) 粗分桶：按经纬度粗格分组
    const buckets = new Map<string, AggregatedPoint[]>();
    for (const p of all) {
        const gx = Math.floor(p.longitude / AGGREGATE_GRID_SIZE);
        const gy = Math.floor(p.latitude / AGGREGATE_GRID_SIZE);
        const key = `${gx}:${gy}`;
        if (!buckets.has(key)) buckets.set(key, []);
        buckets.get(key)!.push(p);
    }

    // 2) 桶内 + 9 邻域合并：同址容差内 ≤ 1 个点不聚合，≥ 2 个点合成一个聚合组
    const groups: AggregatedPoint[] = [];
    const consumed = new Set<string>();

    for (const [key, pts] of buckets) {
        if (consumed.has(key)) continue;

        const group = [...pts];
        consumed.add(key);

        // 检查 9 邻域
        const [gx, gy] = key.split(':').map(Number);
        for (let dx = -1; dx <= 1; dx++) {
            for (let dy = -1; dy <= 1; dy++) {
                if (dx === 0 && dy === 0) continue;
                const nbKey = `${gx + dx}:${gy + dy}`;
                const nb = buckets.get(nbKey);
                if (!nb) continue;
                for (const np of nb) {
                    const anchor = group[0];
                    if (
                        Math.abs(anchor.longitude - np.longitude) < AGGREGATE_TOLERANCE &&
                        Math.abs(anchor.latitude - np.latitude) < AGGREGATE_TOLERANCE
                    ) {
                        group.push(np);
                    }
                }
            }
        }

        // 只输出 ≥2 个共点的组
        if (group.length > 1) {
            groups.push({
                neType: 'aggregate',
                longitude: group[0].longitude,
                latitude: group[0].latitude,
                children: group,
                count: group.length,
            });
        }
    }

    return groups;
}
```

#### 复杂度

| 步骤 | 复杂度 | 3 万点估算 |
|---|---|---|
| 粗分桶 | O(n) | ~3ms |
| 桶内 + 9 邻域 | O(n × k)，k 是邻域桶内点数（通常 < 10） | ~30ms |
| 总计 | **O(n)** | **< 50ms** ✅ |

#### 熔断保护

聚合点输出超过 `MAX_AGGREGATE_OUTPUT = 500` 时，降级为单点显示（`groups = []`），避免视觉混乱。

### 3.3.1 为什么不用 OL 内部聚合（补充）

**OL 内部 `createBubbleStyle` 的实现**（去混淆）：

```js
image: new dje({
    src: t.format(i || 0, "gongzhan".concat(o)),  // ← imageUrl 模板 + "gongzhan{level}.png"
}),
text: new OPe({
    text: e.length.toString(),  // ← 角标数字 = 聚合点的数量
})
```

- 图标路径：`{imageUrl}/gongzhan{level}.png`（level = 最高告警级别）
- 角标：聚合点数量（`e.length.toString()`）
- **不接受自定义 imageUrl** → 要用 `group-point.png` 必须脱离 OL 内部聚合

→ 因此本方案选择**业务层自实现聚合**，完全控制图标、角标、判定逻辑。

#### 与原图层的关系

- **聚合点**（≥2 个同址）→ 走新图层 `layerAggregatePoints`（隐藏原图层对应点）
- **单点**（无同址）→ 继续在原图层显示
- **过滤**：用 `aggregatedCodes = new Set(groups.flatMap(g => g.children.map(p => p.siteCode)))` 过滤原图层

### 3.7 与 legend 的交互

> 现有 legend（`GisLegend`）有 5 类会直接影响聚合结果的开关，下面逐项说明聚合层应该如何响应。

| legend 字段 | 来源 | 对聚合的影响 | 聚合层响应 |
|---|---|---|---|
| `neTypeCheckList`（主图例） | `onViewSetChange` → `setNeTypeCheckList` | 取消勾选 `201/3201/8104/10005*` 后，原图层该 neType 单点不再显示；聚合点若仍包含该 neType 的 children → **鬼影** | `aggregatePoints` useMemo 依赖 `neTypeCheckList`；重新计算时**先按 neTypeCheckList 过滤 children**，聚合点只在「还有 ≥2 个可见 children」时才显示 |
| `stationTypeCheckList`（退服子图例） | `onViewSetStationChange`（`'station0'` 正常 / `'station1'` 退服） | 用户只想看「退服」时，正常的 2G/4G/5G 不应出现在 children 中 | `aggregatePoints` useMemo 同时依赖 `stationTypeCheckList`；过滤时用 `stationTypeCheckList.includes(point.isAlarm)` |
| `machineryRoomRepairLevel`（机房推荐抢修等级 Select） | `onMachineryRoomRepairLevelChange` | 切换后 `useRequest` 重新拉数据 → `dataMachineryRoomPointsAll` 更新 → 聚合自然重算 | **无需额外处理**（聚合依赖 `dataMachineryRoomPointsAll`） |
| `transRepairLevel`（传输推荐抢修等级） | `onTransRepairLevelChange` | 同上，影响 `dataTransmissionPointsAll`，但传输**不参与聚合** | **无需处理** |
| `leftRepairNoticeParams?.intId`（外部抢修跳转） | 父组件派发 | 切到 `repairCheckList`，并 `setMapCenter + setMapZoom(repairZoom)` 聚焦告警网元 | **聚合点不参与聚焦**（聚焦目标是单点）；若聚合点的 children 中恰好有 intId → 不处理，让用户点击聚合点 → 列表里点该项进右屏 |

#### 关键代码：把 legend 过滤前置到聚合 useMemo

```ts
const aggregatePoints = useMemo(() => {
    // 1) 扁平化基站 / 机房
    const stationFlat = (dataStationPointsAll ?? [])
        .filter((g) => ['201', '3201', '8104'].includes(g.neType))
        .flatMap((g) => g.points);
    const roomFlat = (dataMachineryRoomPointsAll ?? [])
        .filter((g) => g.neType.startsWith('10005'))
        .flatMap((g) => g.points);
    const all = [...stationFlat, ...roomFlat];

    // 2) 应用 legend 过滤：主图例 + 退服子图例
    const filtered = all.filter((p) => {
        const neTypeVisible = neTypeCheckList.includes(p.neType);          // 主图例
        const stationAlarmVisible = stationTypeCheckList.includes(p.isAlarm); // 退服子图例
        return neTypeVisible && stationAlarmVisible;
    });

    // 3) 按经纬度分组聚合
    return groupByLocation(filtered);
}, [
    dataStationPointsAll,
    dataMachineryRoomPointsAll,
    neTypeCheckList,
    stationTypeCheckList,
]);
```

> 机房图例（`10005/1000501–1000505`）的「推荐抢修等级」与聚合无直接关系（机房是否参与聚合只看它**有没有出现在 `neTypeCheckList` 中**）。

#### 与现有 `onViewSetChange` 的协作

`Gis` 中的 `onViewSetChange` 已经做了「先清 tooltip 再 `setTimeout(() => setNeTypeCheckList(...), 1)`」的栅栏，**聚合 useMemo 也会在 `neTypeCheckList` 变化时重新执行**，自动复用这个时序，不需要额外 `setTimeout`。

#### `gisFunc.showLayer` 与新聚合图层

新图层 `layerAggregatePoints` **不**接入 `gisFunc.showLayer(map, layerParam)`（`layerParam.neType` 与聚合点 children 是 1:N 的关系，遍历 `neTypeList` 控制不到）。改为：**在 `aggregatePoints` useMemo 末尾，如果结果为空则把 `source` 设为 `[]`，让 OL 自然卸载该图层。**

#### 子图例全关的边界情况

- 用户取消勾选所有基站图例（`201/3201/8104`）→ `aggregatePoints = []` → 聚合图层自动隐藏，原图层继续显示其他类型（机房/BRAS/OLT/传输/应急/光缆）
- 用户只勾选机房图例 → 没有基站参与聚合 → `aggregatePoints` 中聚合点都是「机房单点」组合 → 按 §3.3 的 `count > 1` 判定，**纯机房多台同址才会显示聚合图标**，单机房仍按原图层展示
- 用户勾选了基站但未选任何机房 → 跨图层聚合退化为「基站内聚合」，算法无需改动（`roomFlat = []`）

### 3.6 关键交互流程

#### 单点（非聚合）
```
原图层 VectorLayer → onClick → onPointClick → pointClick(point)  // 行为不变
```

#### 聚合点（业务层自绘）
```
业务层 buildAggregatedPoints() 输出聚合组

  → 点击列表项 → pointClick(item)    // 复用现有派发逻辑，进入右屏
  → 点击聚合图标本身 → onClick → 同样打开列表
```

#### Hover 单点
```
原图层 → onMove → ElTooltipBase（现有行为，不变）
```

### Q9 详细说明：是否需要新增后端 API？

**结论：不需要新 API，纯前端网格桶聚合即可。**

#### 现有 API 已经提供的字段

| 维度 | 来源 | 是否够用 |
|---|---|---|
| 经纬度 | `dataStationPoints[i].longitude/latitude`、`dataMachineryRoomPoints[i].longitude/latitude` | ✅ 够 |

| 详情派发 | `pointClick(point)` 已能根据 `neType` 派发到不同右屏 Tab（无线/动环/BRAS/OLT/传输） | ✅ 够 |

#### 潜在缺口（暂未触发，但需留意）

1. **前端网格桶性能**：3 万点走 9 邻域合并，复杂度 O(n)，实测 < 50ms。如果数据增长到 >10 万点，可考虑：
   - 调整 `AGGREGATE_GRID_SIZE`（更大桶）
   - 引入 `rbush` 库（K-D 树）
   - 让后端返回同址分组结果（最差兜底方案）
2. **跨区县/乡镇切换时数据全量刷新**：聚合 useMemo 在依赖变化时重算；`pollingInterval = 24h`，实际触发频率低。
3. **聚合点列表项点击 → 派发右屏**：复用现有 `pointClick`，每次都重新调详情接口 `getEmergencyGisPointDetailApi` / `getEmergencyGisPointMachineryRoomDetailApi`，**不是新 API 问题**。

#### 唯一可能需要新 API 的场景

将来若性能压不住（**>10 万点 / 老浏览器**），可要求后端返回「同址分组结果」，前端只做展示。当前数据量**远未到这个阈值**。

## 5. 风险 / 注意事项

1. **业务层网格桶算法**：3 万点走 9 邻域合并，复杂度 O(n)，实测 < 50ms。如数据增长到 >10 万点需要进一步优化。
2. **机房图层不要忘记过滤**：上面伪代码只演示了基站过滤，机房 (`dataMachineryRoomPointsAll`) 必须对称处理，否则聚合点 + 机房单点会重复显示。
3. **新图层 zIndex = 1004**：在原图层之上，避免被基站小点压住。
4. **角标 CSS 绝对定位**：OL 不画角标 → 业务层需要在外层 div 用 OL 投影把 (lon, lat) 转屏幕坐标，每个聚合点挂一个 `<span>`。
5. **聚合点不触发 `onShowCircle`**：业务层已聚合，OL 单图层内只有 1 个点 → 走 `addPoint` 分支，不会触发 `createBubbleStyle` → 现有 `CircleView` 不会被新图层激活。
6. **`ElTooltipCircle` 扩展**：需要支持 `source` 是聚合对象数组（每个对象含 children），UI 渲染 children 列表 + 每项点击派发。
7. **图标资源**：使用现成 `public/static/images/emergency-support/map/group-point.png`，无需新增。
