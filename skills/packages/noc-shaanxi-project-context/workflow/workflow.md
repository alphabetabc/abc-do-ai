# 项目工作流规范

> 本文档是 noc-shaanxi-project-context skill 的正式工作流规范，所有任务按此执行。生效日期：2026-09-09。

## 1. 总则

1. **审批硬门槛**：阶段推进必须经用户明确批准，AI 不得自行跨越。
2. **先读后写、不猜**：任何文档/代码产出前先 Read 相关源码与既有文档。
3. **卡住就上报，不自作主张**：发现需求遗漏、边界冲突、依赖阻塞时，回到上阶段或询问用户，不扩大范围。
4. **文档与代码同寿命**：实现完成后必须回填设计文档，文档失真视为任务未完成。
5. **不多不少**：只做被要求的事，不做「不做清单」里的项，防过度设计。

## 2. 流程总览

```
用户提需求
  │
  ▼
阶段一：需求分析（禁写代码）
  澄清 → 结构化 → 审批 ──否──► 修改需求文档，再审批
  │ 用户批准（硬门槛①）
  ▼
阶段二：编码实现
  技术设计 → 编码 → 测试 → 修复 → 文档回填
  │ 验收清单全过（硬门槛②）
  ▼
任务归档（plans/done/）
```

回退规则：阶段二任一子步发现需求问题 → 停止编码 → 在需求文档中补「变更记录」→ 重新过硬门槛① → 继续。

## 3. 阶段一：需求分析

### 输入

- 用户原始描述（对话 / `pm/` 下已有方案文档 / `backend-api-docs/` 接口文档）
- 相关既有代码与设计文档（AI 必须先 Read）

### 3.1 系统性提问（grill me）

AI 主动向用户澄清需求，问题按以下维度组织：

| 维度 | 典型问题 |
| --- | --- |
| 目标 | 最终状态是什么？做完后用户看到什么？ |
| 功能边界 | 哪些必须做？哪些明确不做？ |
| 数据 | 数据从哪来（接口/字段/刷新方式）？以 `backend-api-docs/` 为准，不虚构 |
| 交互 | 什么触发？异常时表现？ |
| 技术 | 涉及哪个页面/模块？有无依赖版本约束（国产数据库适配）？ |
| 验收 | 怎么判定「做对了」？逐条列出可勾选的验收条件 |

提问纪律：
- 一次最多 4 个问题，用 AskUserQuestion 结构化提问。
- 能通过 Read 代码/文档自答的，不问用户。

### 3.2 需求文档

统一存放于本 skill 的 `plans/`，命名 `task-<date>-<seq>-<slug>.md`，结构：

```markdown
# <任务标题>
## 背景与动机
## 用户故事（As a... I want... So that...，按角色分条）
## 功能列表（必须做，编号 F1/F2...）
## 不做清单（明确排除项）
## 非功能需求（性能/兼容/依赖版本约束）
## 业务规则（数据映射、状态流转、特殊逻辑）
## 验收标准（可勾选 checklist，编号 A1/A2...）
## 技术设计（阶段二 2.1 产出，回填于此）
## 变更记录（阶段二回退时追加）
## 审批记录（状态：待审批/已批准，日期 + 批准人）
```

### 3.3 质量检查点（硬门槛①）

AI 完成需求文档后自检，全部通过后提交用户审批：

- [ ] 每个功能点都能追溯到用户原话或用户确认的回答
- [ ] 不做清单非空（至少排除一项防范围蔓延）
- [ ] 验收标准全部可独立判定（无「体验良好」类模糊词）
- [ ] 涉及的数据来源已对照 `backend-api-docs/` / 实际 controller 验证
- [ ] 涉及 `docs/` 改动的，走 `docs/` 独立审批流程（见仓库根 `AGENTS.md`）

**输出**：用户批准的需求文档（`plans/task-*.md`）。

## 4. 阶段二：编码实现

### 输入

已批准的需求文档 + 相关源码（实现前必须 Read）。

### 4.1 技术设计

默认写入需求文档「技术设计」章节；任务复杂或涉及模块级演进时，与用户确认后独立为 `design/modules/<模块>/` 设计文档。

内容要求：
- 改动点清单：文件级定位（路径 + 函数/组件）
- 依赖顺序：被依赖的先行（类型 → 工具 → 组件 → 页面）
- 复用判断：优先复用既有组件/hooks，三次相似代码才考虑抽象
- 风险标注：导出符号/文件名变更需列受影响引用点；依赖改动需对照国产数据库适配文档（`design/modules/chinese-database-adapter/`）

### 4.2 编码

- 遵循仓库 eslint/prettier，不引入新规则、不擅增依赖
- 提交前跑 `pnpm run lint`

### 4.3 测试与修复

测试要求分层执行：

| 层级 | 要求 | 说明 |
| --- | --- | --- |
| tsc 类型校验 | **必须通过（最低门槛）** | 不论任务大小，`tsc` 无类型错误 |
| lint | 必须通过 | `pnpm run lint` 无报错 |
| 运行验证 | 尽量执行 | `pnpm start` 页面可正常运行 |
| 单测/组件测试 | 有则跑、覆盖则过 | 项目内存在对应测试时执行并通过 |

- 按验收标准逐条核对；缺陷修复记录在需求文档「变更记录」或提交说明中。

### 4.4 文档回填

- 技术设计决策、实现细节、踩坑回填到 `design/modules/<模块>/` 对应文档
- 文档引用一律仓库相对路径纯文本（`env/rules/01-link-format.md`）

### 4.5 质量检查点（硬门槛②）

- [ ] 验收标准 A1...An 全部勾选
- [ ] `tsc` 类型校验通过（最低门槛）
- [ ] `pnpm run lint` 无报错
- [ ] 需求文档与设计文档已回填更新，无死链接
- [ ] 涉及导出符号/文件变更的，引用处全部更新
- [ ] 需求文档审批记录更新，任务归档至 `plans/done/`

## 5. 角色职责

| 角色 | 阶段一 | 阶段二 |
| --- | --- | --- |
| **用户** | 回答澄清提问；审批需求文档（硬门槛①）；验收最终结果 | 审批重大技术方案；验收（硬门槛②） |
| **AI** | 系统性提问；Read 代码自答可自答项；产出需求文档；自检清单 | 技术设计、编码、测试、修复、文档回填；发现需求问题即停并上报 |
| **文档 owner**（如涉及他人维护的 `docs/`） | 审批相关 `docs/` 草案 | —— |

## 6. 状态与流转

- 任务状态：`待审批 → 已批准 → 实现中 → 已完成(归档)`，记录在需求文档「审批记录」章节。
- 回退：阶段二发现需求遗漏 → 停止编码 → 需求文档补「变更记录」→ 重新硬门槛①。
- 卡死处理：同一阻塞连续出现且无法推进 → AI 明确告知用户阻塞原因并暂停，不自行绕过。
- 归档：`plans/task-*.md` → `plans/done/`。

## 7. 与既有机制的衔接

- `pm/` 下已有详细方案文档的任务：方案文档视作需求文档的输入，仍需整理成 `plans/task-*.md` 标准结构并过审批。
- `docs/` 改动：需求文档里的 docs 相关条目即提案草案，走 `AGENTS.md` 的 docs 审批。
- git：日常 `develop`，完成后 cherry-pick 到 `develop-cmcc-fault-center`（仅 emergency-support 能力），见仓库根 `AGENTS.md`。
