## 发展目标

把大屏生产从"人工拼装"转为"规则驱动的自然语言生成"。

判断依据：现有大屏体系（widget 注册机制、交互字段派发、组件库）已经具备组件化与联动能力，瓶颈不在画图，在"把业务需求翻译成可生成的结构"这一层。我的目标是把这一层做出来：定义一套**组件无关的大屏 DSL Schema**，打通"自然语言 → Schema → 渲染"链路，并沉淀成可脱离本项目复用的规则资产（skill / 规范）。

## 总结自己目标

一句话：大屏这块最值钱的不是页面，是把需求变成可生成结构的翻译层——组件和联动机制已经有了，我要做的是把这套能力显性化成 Schema 和生成规则，让大屏从"每个都手搓"变成"说得出来就生成得出来"，而且这套规则换个项目、换个组件库照样能用。

## 具体执行内容

1. **大屏 DSL Schema 设计**：梳理既有 widget 体系，抽象出组件无关的 Schema 规范（widget 类型 / 布局 / 联动 / 数据绑定），并通过适配层对接现有组件库
2. **自然语言 → Schema 翻译链路**：基于 LLM + Schema 约束，实现从一句话需求生成结构化大屏描述，含校验与纠错规则
3. **生成链路验证与规则沉淀**：用一个小闭环 Demo（一句话生成含地图 + 图表 + 联动的单屏）验证全链路，并将 Schema 规范、翻译规则、踩坑结论封装成可复用 skill

## 附：架构口径（备他追问时用，不随计划提交）

```
┌─────────────────────────────────────┐
│  Schema 规范（widget/布局/联动/数据绑定） │ ← 通用：纯结构定义，不含本项目概念
├─────────────────────────────────────┤
│  自然语言 → Schema 的翻译规则           │ ← 通用：prompt 模板、校验规则、纠错策略
├─────────────────────────────────────┤
│  组件适配层（adapter）                  │ ← 本项目：Schema widget 类型 → ui 组件
├─────────────────────────────────────┤
│  现有 large-screen 渲染层              │ ← 本项目：不动
└─────────────────────────────────────┘
```

- 上面两层不知道下面是谁：Schema 里 widget 类型是抽象名（map / chart-bar / kpi-card / panel / decoration…），翻译层产出纯 JSON
- 换项目只重写适配层，Schema 规范、翻译规则、校验策略原样带走
- Demo 阶段抽象 6–8 个 widget 类型即可，够闭环，不过度设计
