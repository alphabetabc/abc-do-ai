### 3.2 尺寸计算 — getGroupSizePosition

**文件**：`src/designer/renderer/utils.ts` L322-395

遍历 children，对每个子节点读 `data.config.{width,height,left,top}`，计算包围盒：

- `left` = min(所有子节点 left)
- `top` = min(所有子节点 top)
- `width` = max(left + width) - min(left)
- `height` = max(top + height) - min(top)

### 3.3 子节点坐标归一化 — resetChildrenPosition

**文件**：`src/designer/renderer/utils.ts` L397-412

成组时把子节点的 `left/top` 减去 group 的 `left/top`，转为**相对坐标**：

```ts
export function resetChildrenPosition(children, groupPosition) {
    return children.map((item) => ({
        ...item,
        data: { ...item.data, config: {
            ...item.data.config,
            left: item.data.config.left - groupPosition.left,
            top: item.data.config.top - groupPosition.top,
        }},
    }));
}
```

### 3.4 拆组 — splitGroup

**文件**：`src/designer/renderer/utils.ts` L484-516

- 仅对 `type === 'group'` 生效（L492 守卫）
- 子节点 `left/top` 加回 group 的 `left/top`，还原为画布绝对坐标（与 `resetChildrenPosition` 互逆）
- 树结构：group 节点在父级 children 数组中被其 children 整体替换

### 3.5 bounds 重算 — recalcGroupBounds

**文件**：`src/designer/DesignerContent.tsx` L276-328

- **触发**：`reduxStore.subscribe(recalcGroupBounds)` 订阅 store 变化
- **条件**：选中组件的父级存在且非 ROOT_ID
- **算法**：对父级 children 调 `getGroupSizePosition` 重算包围盒，若尺寸变化则 `resetChildrenPosition` + `mergeFieldConfig` 更新父 group
- **防重入**：`isRecalcRef` 防止 setComponents 触发的回调再次进入

### 3.6 渲染

**分发**：`src/designer/renderer/generator.tsx` L25-26 / L63-66

`args.type === FIELD_COMP_TYPES.GROUP` → `<GroupField>`

**GroupField**：`src/designer/renderer/components/group-field/index.jsx` L57-331

- `slider === true`：用 `react-slick` 的 `Slider` 包裹 children（轮播）
- `slider === false`：直接渲染 children

**position: relative**：`group-field/index.less` L1-4 `.group-container { position: relative }`（作为子节点绝对定位的定位上下文）

### 3.7 约束规则

- **能嵌套**：代码无任何显式禁止，`syncGroupSize2Children` 递归处理子节点支持嵌套
- **能放入 layout-block**：`dropToGroup` 仅禁止 layout-block 入 layout-block，不检查 group
- **创建方式**：右键"成组"（`generatorGroup`），不能从物料面板拖入

## 五、group 与 layout-block 对比

| 维度 | group | layout-block |
|---|---|---|
| **children** | 有（容器） | 有（容器） |
| **能否嵌套** | 能（无限制） | **不能**（双重保险） |
| **尺寸来源** | 子节点包围盒（`getGroupSizePosition`） | 预设/手动（`PRESET_BLOCK_LIST`） |
| **尺寸→子节点同步** | resize 时 `syncGroupSize2Children` 按比例缩放 | 拖入时 `syncLayoutBlockSize2Children`（单子节点撑满） |
| **子节点可移动** | 默认可移动 | `enableMovable: false` |
| **创建方式** | 右键"成组" | 物料面板预设拖入 |
| **空状态** | 无占位符 | `LayoutBlockProxy` 显示尺寸 |
| **轮播** | 原生 `GroupField` 支持 | children > 1 时复用 `GroupField` + 强制 slider |
| **DOM 高亮** | 无 | 完整的 highlight/downplay/查找体系 |
| **拆组** | `splitGroup` 支持 | 无（只能删除） |
| **配置面板** | `configuration-panel/group/` | `layout-block/config/ConfigurationPanel.tsx`（含尺寸联动） |

## 七、拓展分析

### 7.1 拓展边界判断

| 能力 | 属于框架 | 属于业务 | 理由 |
|---|---|---|---|
| 变体定义（field 叶子 / group 容器 / layout-block 不可嵌套） | ✅ | | 变体定义是数据模型层面的结构约束，不是业务规则 |
| type 字段类型约束 | ✅ | | 类型定义属于框架 |
| 尺寸计算算法（getGroupSizePosition） | | ✅ | 依赖业务字段 width/height/left/top |
| 预设块（PRESET_BLOCK_LIST） | | ✅ | 不同业务预设不同 |
| DOM 高亮机制 | | ✅ | 依赖具体 DOM 结构和 CSS |
| 轮播能力 | | ✅ | 依赖 react-slick 等业务库 |
| 创建/拆组算法 | | ✅ | generatorGroup/splitGroup 依赖业务语义 |
| 子节点尺寸同步 | | ✅ | syncLayoutBlockSize2Children 依赖业务字段 |

### 7.2 三层拓展方案

#### 第一层：文档认知（必做，零风险）

在 `01-data-model.md` 补充"节点类型变体"章节，描述三种变体的结构语义：

- field：叶子节点，无 children
- group：可嵌套容器，尺寸由子节点包围盒决定
- layout-block：不可嵌套容器，尺寸由预设或手动设定

框架核心代码不变，文档明确变体定义。

#### 第二层：类型层拓展（可选，低风险）

给 `TreeNode` 加 `TType` 泛型参数：

```ts
export interface TreeNode<
    TData = unknown,
    TType extends string = string,
> {
    uniqueId: string;
    type: TType;
    data: TData;
    children?: TreeNode<TData, TType>[];
}
```

业务侧：`TreeNode<WidgetData, 'field' | 'group' | 'layout-block'>`。框架核心仍不判断 type，但类型层面有约束。

#### 第三层：变体校验插件（可选，中风险）

在 structure tools 插件或独立插件中加**变体约束校验钩子**，让 `setTree` 前可以校验树结构是否满足变体规则（如 layout-block 不嵌套、field 无 children）。业务可选注册。

## 八、结论

1. **FIELD_COMP_TYPES 是节点类型变体，不是业务规则**。三种变体（field/group/layout-block）描述的是节点在树结构中扮演的角色及其结构约束。

2. **框架当前完全忽略 type 语义**是合理的抽象层级——框架核心只管"树结构怎么存"，不管"树结构怎么变"。但**变体定义本身应该被框架文档认知**。

3. **变体的具体算法（尺寸计算/创建/拆组/DOM 高亮/轮播）是业务的**，框架不内置。框架的 structure tools 插件提供注册机制，业务实现具体算法。

4. **拓展建议**：第一层（文档认知）必做，第二层（类型约束）可选，第三层（变体校验）视需求而定。不急于一步到位，先落文档，再逐步拓展。
