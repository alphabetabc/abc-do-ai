## 0. 一句话回答（完成标准自检）

> **byId 当前被谁写？**
> （1）reducer 的 `setComponents` / `setState` 内部 `buildIndex` 全量重建；
> （2）reducer 的 `updateFieldConfig` 直接 patch `byId[id]`（只此一处绕过 buildIndex，是双源脱钩的根源）。
>
> **byId 当前被谁读？**
> （1）`useFieldConf(uniqueId)` hook 订阅 `byId[id]`（字段级渲染）；
> （2）事件回调中 `store.getState().designerCanvas.byId[id]` 同步读（对齐、拖拽 onDragStop、layer-manager 成组/拆组等）；
> （3）`recalcGroupBounds` 用 byId 重算 freshChildNodes；
> （4）`mergeByIdIntoTree` 的 `fieldPreserve` / `byIdWins` 方向读 byId 合并到树；
> （5）`getSaveableComponents` 读 byId 合并到 stale 树用于保存序列化。
>
> **如果 byId 变成纯派生（只读，仅由 buildIndex 重建），哪些路径会断？**
> 仅 `updateFieldConfig` reducer 的"直接 patch byId"分支会断——需改为 Immer produce 改 components 树，再由 buildIndex 派生 byId。
> 其余读路径（useFieldConf / 事件回调用 byId / recalcGroupBounds）**不会断**：单源后 byId 仍存在，只是来源从"双源写入"变成"纯派生"。
> `mergeByIdIntoTree` / `getSaveableComponents` / `dirtyConfigKeys` / skip 机制会变成死代码（byId 永远等于 buildIndex(components)，无 stale 可合并）。

### 1.3 buildIndex（派生索引重建）

文件：[src/designer/renderer/utils.ts](../../../../src/designer/renderer/utils.ts) L784-L807

- 输入：components 树
- 输出：`{ byId, parentMap }`
- 特性：
  - 只遍历 `node.children`，**不遍历 `node.data.config.drillDown`**（drillDown 是配置数据，不进 byId）
  - `byId[id].data` 是**浅引用**（直接 `= node.data`），禁止 reducer 之外修改
  - `byId[id].dirtyConfigKeys` 在 buildIndex 时重置为空 `Set`（树已重建，字段级更新已合并）
- 性能：440 组件 1-2ms（文档记录）

**关键事实**：
- buildIndex 是单源重构后 byId 的**唯一来源**（纯派生）
- buildIndex 重置 dirtyConfigKeys——这是 dirtyConfigKeys 生命周期的"重置端"

### 1.8 recalcGroupBounds 完整逻辑（双源同步最复杂的边界）

文件：[src/designer/DesignerContent.tsx](../../../../src/designer/DesignerContent.tsx) L278-L383

**触发方式**：`reduxStore.subscribe(recalcGroupBounds)`（非 useEffect，避免 DesignerContentImp 重渲染）

**算法分支**：

```
recalcGroupBounds()
  ├─ isRecalcRef.current === true → return（防重入）
  ├─ 读 selected[0] 的 parentId（来自 parentMap）
  ├─ 取 parent 节点（getFieldNodeById 或虚拟根）
  ├─ freshChildNodes = parents.children.map(c => byId[c.id].data !== c.data ? {...c, data: byId[c.id].data} : c)
  │   ↑ 用 byId 重算子组件 data（因为 updateFieldConfig 只改 byId 不改树，tree 是 stale）
  ├─ getGroupSizePosition(freshChildNodes) 算 bbox
  │
  ├─ shouldSkipGroupRecalc() === true（skip 路径，但当前永远 false——见 §1.9）
  │   ├─ 只更新组尺寸 width/height，不改 top/left
  │   └─ setState({ components: mergeFieldConfig(...) })
  │
  └─ 正常路径（left/top/width/height 变化时）
      ├─ resetChildrenPosition(freshChildNodes) 归一化子组件位置
      ├─ mergeFieldConfig 生成新树 results
      ├─ ⚠️ task-012-2 两步同步：
      │   1. dispatch(updateFieldConfig(parent, {config: 归一化后组位置}))  // 先写 byId
      │      dispatch(updateFieldConfig(child, {config: 归一化后子组件位置}))  // 每个子组件
      │   2. setState({ components: results })  // 再 setComponents 同步树
      └─ isRecalcRef 防重入
```

**关键事实**：
- `freshChildNodes` 包装是双源 stale 防护的核心——单源后 components 永远 fresh，此包装删除
- task-012-2 的"先 updateFieldConfig 再 setComponents"两步同步是双源脱钩的衍生物——单源后简化为单次 setComponents
- `isRecalcRef` 防重入与双源无关（recalcGroupBounds 内 setState 触发 subscribe 重入），单源后仍需保留

### 1.10 dirtyConfigKeys 生命周期

| 阶段 | 位置 | 行为 |
| --- | --- | --- |
| 初始化 | `buildIndex` L796 | `dirtyConfigKeys: new Set()`（每次 buildIndex 重置） |
| 累加 | `updateFieldConfig` reducer L132-L137 | `target.dirtyConfigKeys.add(key)`（patch.config 的 keys） |

- dirtyConfigKeys 永远只增不减：连续字段级更新不触发 setComponents 时持续累积

**关键事实**：dirtyConfigKeys 完全是双源同步的衍生物——单源后 byId 永远等于 buildIndex(components)，不存在"哪些字段被字段级更新过"的问题，dirtyConfigKeys 整个机制删除。
