## 1. 阶段 1+2 的事实复核（基于真代码）

> 本节是本阶段相对阶段 1+2 的**增量贡献**——通过读真实代码发现阶段 1+2 未覆盖的细节。这些发现必须在阶段 4 步骤中显式处理。

### 1.1 ⚠️ 重大修正：60Hz 路径描述是错的

**阶段 1 §1.4 + 阶段 2 §6.1 把 `designer-field/index.tsx L214/L230` 标为 60Hz 路径**——这是基于推断，**与实际代码不符**。

**真实代码（designer-field/index.tsx L176-L190 + L192-L242 + L244-L259）**：

> ⚠️ r3.3 说明：下表 designer-field 行号统一采用"函数体第一行"（与 r1 A 视角验证一致），实际函数声明行比此行号少 1（如 onDragHandle 声明在 L175，函数体第一行 L176）。若阶段 4 需精确定位，以函数声明行为准。

| 回调 | 触发频率 | 是否 dispatch | 路径 |
| --- | --- | --- | --- |
| `onDragHandle` (L176) | 60Hz | **不 dispatch**（100ms throttle + 仅 setLocations + dragFieldInLayoutBlock） | 高亮 layout-block 元素（drag2layoutBlock.ts L21-L29 的 `LAYOUT_BLOCK.layoutBlockElement.highlight/downplay`），**不写 Redux** |
| `onDragStopHandle` (L192) | **拖拽结束时 1 次** | **不直接 dispatch**——通过 `onValueChange!(...)` 回调通知父级 DesignerContent，由 DesignerContent 内的 `useUpdateFieldConfig` 实例 dispatch（group: 1 次）+ 多选子组件循环 (N-1 次) |
| `onResizeHandle` (L244) | **60Hz 但内部 100ms throttle** → **10Hz** | dispatch setComponents | 每次 `getResizedComponents` 走 setComponents |

**结论**：

1. **`onDrag` 期间完全不 dispatch**——所以 `useUpdateFieldConfig` 在拖拽期间 0 调用
2. **`onDragStop` 只在拖拽结束时 1 次触发**——多选时 N 次 dispatch updateFieldConfig（每个子组件 1 次）
3. **真正的热路径是 `onResize`**：10Hz × setComponents → 内部走 mergeByIdIntoTree + buildIndex（单源后仅 buildIndex）
4. **stage 1+2 误判的 60Hz 路径不存在**——`dragFieldInLayoutBlock` 是只读 store + UI 高亮，不影响 Redux state

**对阶段 4-5 的影响**：

- **元计划 §5.3.3 60Hz 路径风险评估需要重新写**：真正的风险在 `onResizeHandle` 的 10Hz setComponents，而非 onDragStop 的"60Hz updateFieldConfig"
- **`onDragStop` 多选 N 次 dispatch** 是新的次要风险点（一次拖拽结束时 N × updateFieldConfig），需在性能验证中测量
- **元计划 §6.3 回退措施中"对 `useUpdateFieldConfig` 拖拽路径加 rAF 节流"**实际**不需要**——onDragStop 是单次触发，不需要节流；正确做法是测量 onResize 路径实测帧率

### 1.2 useFieldConf 的 dirtyConfigKeys 引用陷阱（阶段 1+2 未察觉）

**utils.ts L784-L807 buildIndex 每次创建新 Set**：

```ts
byId[node.uniqueId] = {
    uniqueId: node.uniqueId,
    type: node.type,
    parentId,
    data: node.data, // 浅引用
    dirtyConfigKeys: new Set(), // ⚠️ 每次 buildIndex 都新建！
};
```

**store/designer/hooks.ts L86-L90 useFieldConf 用 shallowEqual**：

```ts
export const useFieldConf = (uniqueId: string) =>
    useSelector(
        (s: RootReducerState) => s.designerCanvas.byId[uniqueId],
        shallowEqual,
    );
```

**含义**：

- `shallowEqual` 比较 `dirtyConfigKeys` 引用
- 每次 `setComponents` → buildIndex → 新 Set → 与旧 Set 浅比较不等 → `useSelector` 判定变化
- **任何 `setComponents` 都会触发所有 `useFieldConf` 订阅组件 re-render**（440 组件 → 440 个 DesignerField 同时重渲染）

**等等**：但 `byId[id]` 整个对象也是 buildIndex 时新建的——`shallowEqual` 浅比较第一层（uniqueId/type/parentId/data/dirtyConfigKeys 引用），整个对象引用变化本身就触发 re-render。

**实际结论**：
- `setComponents` 本来就触发所有 byId 订阅 re-render（因为 byId 整对象引用变化）
- `dirtyConfigKeys` 是叠加问题，但不是主要问题
- **单源后**：`dirtyConfigKeys` 字段删除（决策 5）→ FlatField 字段减少 → shallowEqual 比较项减少 → 极微小性能提升（不重要）

**对阶段 4 的影响**：
- 决策 5（删除 dirtyConfigKeys）正确，但**不应该在动机说明中过度强调性能收益**——这只省了一个 Set 引用的比较
- 真正重要的是**删除 dirtyConfigKeys 语义本身**：避免 setComponents 后用错值合并（与决策 1 一致）

> ⚠️ **r2.2.1 修正（删除理由排序）**：删除 dirtyConfigKeys 的核心理由按优先级排序如下（避免读者因"性能收益小"而误判删除优先级）：
> 1. **语义上不需要了**（最强理由）：单源后 mergeByIdIntoTree 删除，没有合并方向判断需求，dirtyConfigKeys 失去消费者
> 2. **简化 FlatField 接口**：减少一个字段，降低心智负担
> 3. **微小性能收益**：shallowEqual 少比较一个 Set 引用（可忽略，但顺带获得）

### 1.3 ⚠️ 新风险：useOnDrop mutation 与单源后 setComponents reducer 的 Immer 契约冲突

**useOnDrop.ts L28 + L61 真 mutation**（阶段 1 §1.14 已记录）：

```ts
targetFieldConfig.children.unshift(dropFieldConfig);  // L28 mutation
targetParentChildren.splice(dropPosition === -1 ? index : index + 1, 0, dropFieldConfig);  // L61 mutation
```

**当前路径**：`useOnDrop` → trigger → `setState({ components: getComponents() })` → `dispatch(setComponents(payload))` → reducer 内部 `mergeByIdIntoTree(payload, state.byId, 'fieldPreserve')`

**单源后路径**：`useOnDrop` → trigger → `setState({ components: getComponents() })` → `dispatch(setComponents(payload))` → reducer 改为 `produce(state, draft => { draft.components = payload; ... buildIndex(payload); ... })`

**关键问题**：

1. `payload` 是 mutated tree（useOnDrop L28/L61 直接改 children 数组）
2. `produce(state, draft => { draft.components = payload; })` —— Immer 接收 mutated tree 作为新 components
3. **Immer 会尝试冻结 draft.components**（在 setAutoFreeze 默认开启下）—— mutated children 数组可能已被改过引用，Immer 信任它但不冻结
4. **更严重的**：`buildIndex(draft.components)` 内部读取 children，可能遇到 L30 的 `targetFieldConfig.children = LAYOUT_BLOCK.layoutBlockElement.syncLayoutBlockSize2Children(...)`——这一步 mutate 后又重新赋值

**Immer 与 mutated tree 的交互**（基于 Immer 9.x 文档）：
- Immer produce 接收 mutated tree，**不会立即冻结**（freeze 推迟到 produce 回调完成）
- Immer 创建 draft Proxy，但对未通过 draft 访问的对象（即 mutated tree 中已存在的对象）不创建 Proxy
- 这些对象在最终 produce 输出时**不被冻结**，但**对 reducer 内部修改是可见的**
- 实际后果：mutated tree 内容正确（mutation 已经做了正确的事），但 Immer 的不可变契约被破坏，**未来对该 reducer 的修改可能踩雷**

> ⚠️ **r3.7 假设标注（A1）**：上文"基于 Immer 9.x 文档"是**未验证假设**——阶段 4 步骤 0 前需 grep `package.json` 确认 immer 实际版本（若非 9.x，上述 freeze/draft 行为描述需复核）。
>
> ⚠️ **r3.7 假设标注（A8）**：§2.2.3 修复方案注释"setChildren 已经 immutable"是**未验证假设**——阶段 4 步骤 1a 实现前需读 setChildren 实现（utils.ts）确认其返回新数组而非 mutate 原数组。若 setChildren 实际有 mutation，修复方案需调整。

**对阶段 4 的影响**：

- useOnDrop mutation 修复**必须**在单源重构**之前**或**同步**完成（决策 13 方案 B）
- 修复方案（L28/L61 改写）：

### 1.4 ⚠️ 隐 bug：reducer setState 的 `'components' in action.payload` 风险

**designer-canvas.ts L94**：

```ts
case 'designerCanvas/setState': {
    return produce(state, (draft) => {
        Object.assign(draft, action.payload);
        // 兼容旧调用方：payload 包含 components 时同步重建索引
        if ('components' in action.payload) {
            // ...
        }
    });
}
```

**`in` 操作符的隐患**：
- `'components' in obj` 对原型链上的属性也返回 true
- 如果 `Object.assign(draft, action.payload)` 把 action.payload 的原型链属性也复制过来，可能导致误判
- 实际风险低：action.payload 通常是普通对象字面量，无原型链污染

**对阶段 4 的影响**：
- 阶段 4 步骤 4（改 setState reducer）时顺手用 `Object.prototype.hasOwnProperty.call(action.payload, 'components')` 替代 `'components' in action.payload`，更严谨
- **优先级：低**——不属于双源同步问题，是顺手优化

> ⚠️ **r2.1.3 修正（行为变更显式化）**：若改用 `action.payload.components !== undefined`，存在**隐蔽的行为不一致**：
> - `'components' in { components: undefined }` → `true`
> - `{ components: undefined }.components !== undefined` → `false`
>
> 即：若有调用方传入 `{ components: undefined }`（虽不合理，但理论上可能），改造后**不会触发 rebuildIndex**，导致索引不同步。这属于"隐 bug 修复引入新隐 bug"的典型模式。
>
> **推荐方案**（保持行为一致）：用 `Object.prototype.hasOwnProperty.call(action.payload, 'components')` 替代 `'components' in`——既避免原型链隐患，又保持"key 存在即触发"的语义。
>
> **备选方案**（明确改变行为）：若有意改为"传 undefined 不视为有 components"，需在文档中显式声明此行为变更，并在调用方约定中补充"禁止传 `{ components: undefined }`"。**不建议无声无息地改**。
>
> 经 r2 C 视角交叉验证：所有已知调用方（toolbar/index.js L367 导入配置 / configuration-panel/page/index.jsx L28/L37 / DesignerContent.tsx L163/L166 setState 兼容函数）均传正常值，未发现传 undefined 的情况——故推荐方案（hasOwnProperty）最安全。

> ⚠️ **r1.6 修正（补 DesignerContent L154 同模式）**：§1.4 原文只覆盖了 reducer L94 的 `'components' in`，遗漏了 `DesignerContent.tsx L154` 的 `setState` 兼容函数内部**也用了** `'components' in nextState` 判断（与 reducer L94 同模式）。
>
> **阶段 4 步骤 4 必须同步改 DesignerContent L154**：`'components' in nextState` → `Object.prototype.hasOwnProperty.call(nextState, 'components')`，否则 DesignerContent 侧的同模式残留，未来可能踩同样的原型链隐患。

### 1.5 阶段 1+2 未察觉的引用传递细节

**reducer L82-L88 setComponents**：

```ts
return produce(state, (draft) => {
    const mergedComponents = mergeByIdIntoTree(action.payload, state.byId, 'fieldPreserve');
    // ...
});
```

**注意**：`mergeByIdIntoTree` 接收 `state.byId`（不是 `draft.byId`）——这是正确的，因为在 produce 回调内 draft.byId 还未被修改；我们要读**旧 byId** 来合并**新 payload**。

**单源后**：

```ts
return produce(state, (draft) => {
    draft.components = action.payload;
    // buildIndex 接收 action.payload（不在 draft 上的对象），所以单独调用
    const { byId, parentMap } = buildIndex(action.payload);
    draft.byId = byId;
    draft.parentMap = parentMap;
});
```

**风险**：`buildIndex(action.payload)` 在 produce 回调**外**创建新对象（byId/parentMap），然后赋值给 draft——这是 Immer 允许的（赋值给 draft 自动追踪）。

**含义**：阶段 2 决策伪代码（在 produce 内调 buildIndex）有问题——buildIndex 应在 produce 内调用，但接收 `draft.components`（不是 action.payload）：

```ts
return produce(state, (draft) => {
    draft.components = action.payload;
    const { byId, parentMap } = buildIndex(draft.components);  // ← 这里
    draft.byId = byId;
    draft.parentMap = parentMap;
});
```

Immer 允许读 draft 引用（只是不能触发 freeze 的写入），buildIndex 是纯读 + 新建对象，安全。

**对阶段 4 的影响**：
- 阶段 2 决策 2 伪代码 L136 写 `buildIndex(draft.components)`——已正确
- 阶段 4 步骤 3 实现时**按这个写法**，避免 Immer 误报

**伪代码（基于阶段 2 决策 2，结合 §1.5 修正 + r1.1/r2.1.2 防御性编程）**：

> ⚠️ **r1.1 修正**：parentMap 反向追踪必须加最大深度保护，否则若 parentMap 出现循环引用（如未来 bug 导致 `parentMap['A']='B'` 且 `parentMap['B']='A'`），reducer 会死循环 → 浏览器冻结。

> ⚠️ **r2.1.2 修正**：沿路径 `find` 节点必须检查返回值，否则若 parentMap 与树不一致（异常输入），`node` 变 undefined 后 `node.data = ...` 抛 TypeError → reducer 崩溃 → 应用白屏。
>
> ⚠️ **r1.3.6 注释**：`config: patch.config ? {...node.data.config, ...patch.config} : node.data.config` 是**浅合并**——深嵌套字段（如 `config.style.color`）会被整体覆盖。与现状 reducer 行为一致（非新增风险），但调用方需注意传完整对象。

```ts
case 'designerCanvas/setComponents': {
    return produce(state, (draft) => {
        draft.components = action.payload;
        const { byId, parentMap } = buildIndex(draft.components);
        draft.byId = byId;
        draft.parentMap = parentMap;
    });
}
case 'designerCanvas/updateFieldConfig': {
    const { uniqueId, patch } = action.payload;
    // 边界 1：ROOT 是虚拟根，不在 byId/parentMap 中
    if (uniqueId === ROOT_UNIQUE_ID) return state;
    // 边界 2：parentMap 不存在的 id（组件已被删除），忽略
    if (!state.parentMap[uniqueId]) return state;
    return produce(state, (draft) => {
        // 1. parentMap 反向追踪找路径 O(depth)
        //    ⚠️ r1.1：加 MAX_DEPTH 防循环引用（理论上 parentMap 由 buildIndex 从 root 构建不会有环，
        //    但未来 bug 可能导致循环，reducer 死循环是灾难性故障）
        const path: string[] = [];
        let current: string = uniqueId;
        let depth = 0;
        const MAX_DEPTH = 100; // 树深度上限保护
        while (current !== ROOT_UNIQUE_ID) {
            path.unshift(current);
            current = draft.parentMap[current];
            if (!current || depth++ > MAX_DEPTH) return state; // 防循环 + 防异常深
        }
        // 2. 沿路径找到节点
        //    ⚠️ r2.1.2：find 返回值必须检查（parentMap 与树不一致时 node 会变 undefined）
        //    理论上 parentMap 和树一致，这里不会触发；如触发说明数据结构已损坏，需上层排查
        let node: any = draft.components;
        for (const id of path) {
            node = node.children.find((c: any) => c.uniqueId === id);
            if (!node) return state; // 防御性：找不到节点直接退出
        }
        // 3. 修改节点 data（浅合并：深嵌套字段需调用方传完整对象）
        node.data = {
            ...node.data,
            ...patch,
            config: patch.config ? { ...node.data.config, ...patch.config } : node.data.config,
        };
        // 4. buildIndex 重建 byId/parentMap
        //    buildIndex 是纯读 draft.components + 新建对象，不写 draft 本体，安全
        const { byId, parentMap } = buildIndex(draft.components);
        draft.byId = byId;
        draft.parentMap = parentMap;
    });
}
```

#### 4.1.2 真实热路径性能评估（基于 §1.1 修正）

> ⚠️ **r2.1.1 修正**：以下所有数字均为**粗略估算（待基线验证）**，非实测值。估算依据：buildIndex 440 组件设计目标 1-2ms（阶段 2 §6.3 阈值）+ mergeByIdIntoTree 同复杂度量级（两者都是 O(n) 树遍历）。**与 §4.1.1 "基线缺失"不矛盾**——基线需阶段 4 步骤 0 用 Performance API 实测后确认。若实测 buildIndex 显著偏离 1-2ms（如 5ms+），下方"性能更好/可接受"结论需重新评估。

**可接受标准引用阶段 2 §6.3 阈值**：buildIndex ≤ 3ms / 帧率 ≥ 50fps / updateFieldConfig ≤ 3ms（单源后此阈值需重新评估，因 updateFieldConfig 内部多了 O(n) buildIndex）。

**当前双源实现（重构前）**：

| 路径 | 频率 | 内部开销（估算） |
| --- | --- | --- |
| onResize 期间 setComponents | 10Hz | mergeByIdIntoTree O(n) + buildIndex O(n) ≈ 2-4ms × 10 = 20-40ms/秒 |
| onDragStop N 次 updateFieldConfig | 拖拽结束 1 次 × N | O(1) patch byId × N ≈ 0.1ms × 5 = 0.5ms |
| onDrag 期间 | 60Hz | 0（不 dispatch） |
| handleAlign N 次 updateFieldConfig | 对齐按钮 1 次 × N | O(1) patch byId × N ≈ 0.1ms × 5 = 0.5ms |

**单源实现（重构后）**：

| 路径 | 频率 | 内部开销（估算） |
| --- | --- | --- |
| onResize 期间 setComponents | 10Hz | buildIndex O(n) ≈ 1-2ms × 10 = 10-20ms/秒（**若基线验证 buildIndex ≤ 2ms，则性能更好**） |
| onDragStop N 次 updateFieldConfig | 拖拽结束 1 次 × N | O(depth) produce + O(n) buildIndex × N ≈ 3ms × 5 = 15ms（**若 ≤ 3ms/次阈值成立，拖拽结束 1 次可接受**） |
| onDrag 期间 | 60Hz | 0（不 dispatch） |
| handleAlign N 次 updateFieldConfig | 对齐按钮 1 次 × N | O(depth) + O(n) × N ≈ 15ms（**若 ≤ 3ms/次阈值成立，对齐按钮 1 次可接受**） |

**结论（条件性，待基线验证）**：
- **onResize 路径性能更好**（少一次 O(n) mergeByIdIntoTree）——前提：buildIndex 实测 ≤ 2ms
- **onDragStop 多选性能略降**（从 ~0.5ms 升到 ~15ms）—— 但只发生在拖拽结束时 1 次，若单次 ≤ 3ms 可接受
- **handleAlign 性能略降**（从 ~0.5ms 升到 ~15ms）—— 但只发生在点击对齐按钮时，若单次 ≤ 3ms 可接受
- **真正的高频路径（onDrag 期间）零影响**——根本不走 Redux

**极端场景备注**：循环内连续 dispatch 多次 updateFieldConfig（如 `for (id of ids) dispatch(updateFieldConfig(id, patch))`）性能可能恶化（N × O(n) buildIndex）。建议调用方批量合并后单次 dispatch（如合并为 setComponents）。这是现有最佳实践，非单源重构引入的新问题——但单源后因 updateFieldConfig 内部多了 buildIndex，循环 dispatch 的恶化幅度更大，需在阶段 5 性能验证中关注。

**潜在优化**（不在本次重构范围）：useFieldConf 改为订阅 `byId[id].data` 而非整个 byId[id]，可减少重渲染。但这是 task-019 性能优化范畴。
