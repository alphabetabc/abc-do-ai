## 0. 一句话回答（完成标准自检）

> **重构后 byId 是怎么产生的？** 仅由 `buildIndex(components)` 派生，无任何其他写入路径。
>
> **谁写 byId？** 只有 `setComponents` / `setState`（含 components 时）两个 reducer action 内部调用 `buildIndex`。`updateFieldConfig` 不再直接 patch byId。
>
> **谁读 byId？** （与现状相同）`useFieldConf` 订阅 / 事件回调同步读 / `recalcGroupBounds` 读 freshChildNodes（但 freshChildNodes 包装删除，直接读 components）。
>
> **byId 还会和树脱钩吗？** 不会。byId 永远等于 `buildIndex(components)`，components 是唯一真相源。

## 1. 目标数据流

### 2.1 元计划 §2.1 的 10 个核心决策

#### 决策 1：byId 是否还能被独立写入？

**决策：A. 完全只读（buildIndex 派生）**

**理由**：

**实现要点**：
- `updateFieldConfig` reducer 删除"直接 patch byId"分支（designer-canvas.ts L122-L138）
- 改为 Immer produce 改 components 树（见决策 2）
- reducer 内部 produce 改树后调用 buildIndex 重建 byId

#### 决策 2：updateFieldConfig 改树用什么方式？

**决策：B. parentMap 反向追踪 O(depth) 找节点路径 + Immer produce 改树**

**方案对比**：

| 方案 | 找节点 | produce 改树 | 总复杂度 | 语义 |
| --- | --- | --- | --- | --- |
| A. Immer produce 递归 | 从 root 递归 O(n) 查找 | O(depth) 结构共享复制 | O(n) + O(depth) | 递归 map 找到 id 后修改 |
| B. parentMap 找路径 | parentMap 反向追踪 O(depth) | O(depth) 结构共享复制 | O(depth) + O(depth) | 反向找路径，沿路径 produce |

**关键澄清**（修正元计划 §2.1 原描述）：
- **Immer produce 是惰性的**——只复制被修改路径上的节点，**不会遍历整棵树**
- 方案 A 和 B 的 produce 阶段都是 O(depth) 结构共享复制，无差异
- B 的优势是**找节点**更快（O(depth) vs O(n)），不是 produce 更省
- 440 组件场景：O(depth) 通常 3-5 层，O(n) 最坏 440——B 明显更优

**方案 B 实现伪代码**：

> ⚠️ **review r1 §1.1 修正**：原版伪代码缺 `ROOT_UNIQUE_ID` 防御。`ROOT_UNIQUE_ID = '-'`（utils.ts:22）是虚拟根，不在 byId/parentMap 中（buildIndex walk 起点为 ROOT，byId 只含 children 中节点）。当前 reducer（designer-canvas.ts L122-L124）通过 `if (!target) return;` 天然防御 ROOT——但方案 B 改用 parentMap 反向追踪，当传入 `uniqueId === '-'` 时 while 循环直接跳过、`path = []`，后续 `for (const id of path)` 空循环使 `node = draft.components`（根数组本身），在根数组上 `node.data = {...}` 会创建非法字段或抛 TypeError。伪代码已加边界防御。
>
> ⚠️ **review r1 §3.4 修正**：原版伪代码 `buildIndex(draft.components)` 直接传 Immer draft。现有 `setComponents` reducer（designer-canvas.ts L82-L88）是先 `mergeByIdIntoTree` 返回普通数组 `mergedComponents` 再 `buildIndex(mergedComponents)`——**未直接传 draft**。Immer 在 draft 上调用普通函数可能触发 freeze 异常。伪代码改为先用 `produce` 改树，在 produce 回调结束后**返回新的 state**（produce 返回值即为新 state），再对新 state 的 components 调用 buildIndex——但 buildIndex 也要在 produce 内完成（因为要写 draft.byId/parentMap）。正确做法是：buildIndex 接收 draft.components（Immer 允许读 draft 引用，只是不能在 draft 上调用会触发 freeze 的写入操作——buildIndex 是纯读取 + 新建对象，不写 draft，安全）。

```ts
case 'designerCanvas/updateFieldConfig': {
    const { uniqueId, patch } = action.payload;

    // 边界 1：ROOT 是虚拟根，不在 byId 中，updateFieldConfig 对 ROOT 无意义
    if (uniqueId === ROOT_UNIQUE_ID) return state;
    // 边界 2：parentMap 不存在的 id（组件已被删除），忽略
    if (!state.parentMap[uniqueId]) return state;

    return produce(state, (draft) => {
        // 1. parentMap 反向追踪找路径 O(depth)
        const path: string[] = [];
        let current: string = uniqueId;
        while (current !== ROOT_UNIQUE_ID) {
            path.unshift(current);
            current = draft.parentMap[current];
            if (!current) return; // 组件已删除，忽略
        }

        // 2. 沿路径找到节点 O(depth)
        let node: any = draft.components;
        for (const id of path) {
            node = node.children.find((c: any) => c.uniqueId === id);
        }

        // 3. 修改节点 data（Immer produce 结构共享复制 O(depth)）
        node.data = {
            ...node.data,
            ...patch,
            config: patch.config
                ? { ...node.data.config, ...patch.config }
                : node.data.config,
        };

        // 4. buildIndex 重建 byId/parentMap O(n)
        //    buildIndex 是纯读取 draft.components + 新建对象，不写 draft 本体，安全
        //    （与现有 setComponents reducer L85 buildIndex(mergedComponents) 同语义）
        const { byId, parentMap } = buildIndex(draft.components);
        draft.byId = byId;
        draft.parentMap = parentMap;
    });
}
```

**性能预算**（见元计划 §5.3.2）：
- 单次 updateFieldConfig 总耗时 ≤ 3ms（buildIndex 1-2ms + produce O(depth) < 1ms）
- 60Hz 路径（designer-field onDragStop）：1-2ms × 60Hz = 60-120ms/秒 CPU 占用，**可能可接受**（React 渲染开销远大于此）
- 若实测不可接受（帧率 < 50fps），回退措施：对 `useUpdateFieldConfig` 拖拽路径加 `requestAnimationFrame` 节流

#### 决策 3：buildIndex 每次 setComponents 都全量重建？

**决策：A. 全量 O(n)（先 A，性能不够再 B）**

**理由**：
- buildIndex 在 440 组件下 1-2ms（文档记录），全量重建可接受
- 增量 buildIndex 复杂度高（需追踪哪些节点变化），且单源后 updateFieldConfig 每次都改树，增量收益有限
- 若阶段 5 性能验证不达标（buildIndex > 3ms），再考虑增量

**实现要点**：buildIndex 函数本身不变（阶段 1 §1.3 已摸清），只是调用方从"setComponents + updateFieldConfig 两个路径"变成"setComponents + updateFieldConfig 两个路径都调用"——updateFieldConfig 现在也要调用 buildIndex。

#### 决策 7：recalcGroupBounds 的 task-012-2 修复是否简化？

**简化后伪代码**：

> ⚠️ **review r1 §3.5 修正**：原版伪代码省略了 `components` 的来源。`recalcGroupBounds` 是 `reduxStore.subscribe` 回调（非 useEffect），需显式 `reduxStore.getState()` 读 state，否则会误用闭包中的 stale components。现实现（DesignerContent.tsx L276-L383）显式调用 `reduxStore.getState()`。伪代码已补 state 来源。

```ts
recalcGroupBounds() {
  if (isRecalcRef.current) return;

  // 读 state 来源（review r1 §3.5 补：recalcGroupBounds 是 subscribe 回调，必须显式 getState）
  const state = reduxStore.getState().designerCanvas;
  const components = state.components;

  // 读 selected[0] 的 parentId
  // 取 parent 节点（直接读 components，无需 freshChildNodes 包装）
  const parent = getFieldNodeById(components, parentId);
  const bbox = getGroupSizePosition(parent.children); // 直接读 components

  const results = mergeFieldConfig(components, { parentId: parent.uniqueId }, { config: bbox });

  setState({ components: results });
  isRecalcRef.current = false;
}
```

## 6. 60Hz 路径性能评估

### 6.1 风险路径

`designer-field/index.tsx` L214/L230 的 `onDragStop` 拖拽路径是 **60Hz 触发**（react-rnd 拖拽期间每帧 onChange）。单源后该路径：

| 阶段 | 当前（双源） | 目标（单源） |
| --- | --- | --- |
| updateFieldConfig reducer | O(1) patch byId | O(depth) produce 改树 + O(n) buildIndex |
| 60Hz CPU 占用 | ~0ms × 60Hz = 0ms/秒 | 1-2ms × 60Hz = 60-120ms/秒 |

### 6.2 评估结论

- buildIndex 1-2ms × 60Hz = 60-120ms/秒 CPU 占用，**可能可接受**（React 渲染开销远大于此，440 组件全量 re-render 单次就 10ms+）
- `useFieldConf` 字段级订阅仍然有效——只有被拖组件的 byId[id] 引用变化，其他组件订阅不变，不触发 re-render
- **但当前没有量化基线**（动机说明 §3），无法精确对比"重构前 vs 重构后"

### 6.3 回退措施（若实测不达标）

按优先级排序：

1. **rAF 节流**（调用方改动最小）：对 `useUpdateFieldConfig` 的拖拽路径加 `requestAnimationFrame` 节流，每帧最多 dispatch 一次
2. **lazy buildIndex**（reducer 改动）：dispatch 时不立即 buildIndex，下一帧统一 build——但会破坏 `useFieldConf` 订阅的同步性
3. **增量 buildIndex**（buildIndex 改动）：仅更新变化路径的 byId 条目，O(1) 而非 O(n)——复杂度高，收益有限

**阶段 5 §5.3.3 会定义具体阈值**：buildIndex ≤ 3ms / 帧率 ≥ 50fps / updateFieldConfig ≤ 3ms。不达标时按上述回退措施处理。
