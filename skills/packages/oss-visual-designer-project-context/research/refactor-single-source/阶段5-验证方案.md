## 3. 已修 bug 专项回归（4 项）

> 单源架构从根本上消除了双源同步类 bug 的可能性（树和 byId 永远一致），以下测试仅为验证性确认（阶段 3 §4.3 r2.2.2 修正）。

### 3.1 task-012-1：保存丢失字段级更新

**原 bug**：双源下 byId 有 dirtyConfigKeys 标记但 tree 无，保存时 getSaveableComponents 用 byIdWins 方向合并，dirtyConfigKeys 未正确同步到 tree → 字段丢失。

**单源后根除原因**：保存直接序列化 `designerState.components`（步骤 6），tree 永远是唯一源，无合并方向问题。

**验证**（步骤 6 完成后）：
- [ ] 拖动组件后保存 → 位置字段保留
- [ ] 改名后保存 → 标题字段保留
- [ ] 拖动 + 改名后保存 → 两字段都保留
- [ ] 修改 config 深层字段后保存 → 深层字段保留

### 3.2 task-012-2：组位置漂移 + 子组件二次位移

**原 bug**：双源下 recalcGroupBounds 的 freshChildNodes 包装 + 两步同步（先 updateFieldConfig 再 setComponents）在并发场景下可能拿到 stale byId → 组位置漂移。

**单源后根除原因**：recalcGroupBounds 简化为单次 setComponents（步骤 5），components 永远 fresh，无需 freshChildNodes 包装。

**验证**（步骤 2 完成后先做 mixed-mode 冒烟，步骤 5 完成后做完整 4 项回归）：

**mixed-mode 冒烟**（步骤 2 完成后、步骤 5 未完成前——此时 updateFieldConfig 已改 produce 改树，但 recalcGroupBounds 两步同步仍在，存在 mixed-mode 风险窗口，见元计划 §2.4）：
- [ ] 拖动组内子组件 1 次 → 确认无位置漂移（若漂移，说明两步同步与新的 updateFieldConfig 语义不兼容，需提前执行步骤 5 或回退步骤 2）

**完整回归**（步骤 5 完成后）：
- [ ] 拖动组内子组件 → 组尺寸跟随，子组件不漂移
- [ ] 拖动组内子组件到组外 → 组尺寸正确收缩

- [ ] 连续 3 次 dispatch 后 recalcGroupBounds 只触发 1 次（isRecalcRef 防重入）

## 4. 性能验证（含量化阈值 + 回退标准）

### 4.1 基线数据（已实测，来源：baseline-2026-07-27.md）

> **执行日期**：2026-07-28
> **浏览器**：Chrome 150.0.0.0（Windows 10，16 核 CPU，无节流）
> **测量工具**：perf-baseline.js（performance.now()）
> **完整数据**：见 [baseline-2026-07-27.md](./baseline-2026-07-27.md)

#### 4.1.1 关键基线值（large 场景 = 440 组件）

| 指标 | 基线值（large） | 备注 |
| --- | --- | --- |
| `buildIndex` p95 | **0.2ms** | 纯计算极快 |
| `mergeByIdIntoTree` p95 | **0.1ms** | 单源后删除，节省 0.1ms |
| `setComponents` p95 | **554.1ms** | 含 reducer + Redux 传播 + React 渲染 |
| `updateFieldConfig` p95 | **158.7ms** | 双源下只 patch byId |
| 对齐串行 N=10 | **3731ms** | 当前就有严重问题 |
| 对齐串行 N=440 | **74933ms** | 灾难性 |
| 对齐批量 N=440 | **523ms** | 方案 B 基线 |
| onResize 单次 avg | **1139ms** | 已无法维持 10Hz（5 秒仅触发 2 次） |
| Immer proxy sameRef | **false** | 双源下引用不复用（预期） |

#### 4.1.2 基线关键结论

1. **buildIndex 纯计算开销极小**（440 组件 p95=0.2ms）——单源后每次 updateFieldConfig 跑 buildIndex 的计算开销可忽略
2. **真正性能瓶颈在 React 渲染**——setComponents 554ms 中 reducer 计算仅占 0.04%，其余是 Redux 订阅传播 + React 组件树渲染
3. **对齐操作串行已是灾难**（N=440 达 75 秒）——**方案 B（批量 setComponents）不是备选是必须**
4. **onResize 已无法维持 10Hz**——当前就有严重问题，单源后若不优化会更卡
5. **Immer proxy 引用复用未验证生效**（双源架构下 sameRef=false）——单源后 buildIndex 主动复用，需重测

### 4.4 性能回退决策树

> **重要**：方案 A/B/C 是**正交维度**，不是串行回退。A 解决单次 updateFieldConfig 的引用复用，B 解决对齐 N 次 dispatch 累加，C 解决 onResize 节流。应分别评估，独立触发。D/E 是兜底。

**维度 1：单次性能（reducer 内部）**

```
方案 A：确认 buildIndex 引用复用生效
  ↓ （sameRef 仍为 false 或 updateFieldConfig 仍 > 190ms）
方案 D：增量 buildIndex（仅重建变化路径的 byId 条目）
  ↓ （仍不达标）
方案 E：回退到双源架构（最坏情况，git revert 步骤 2/3/4/5）
```

**维度 2：批量性能（调用方）**

```
方案 B（必做项，非回退项）：对齐操作从 N 次 updateFieldConfig 改为 1 次 setComponents
  ↓ （方案 B 实施后，对齐批量 N=440 仍 > 200ms）
方案 C：rAF 节流（onResize 路径）
```

> **方案 B 定位说明**：基线实测对齐串行 N=10=3731ms、N=440=74933ms（远超阈值），证明方案 B 是**步骤 2 的配套必做项**，不是"等性能不达标再回退触发"。阶段 4 步骤 2 完成时必须同时实施方案 B（作为步骤 2 的补充 commit），否则步骤 2 后对齐操作会从"O(1) × N 串行"变成"O(n) × N 串行"（buildIndex 每次都跑），性能比基线更差。

#### 4.4.1 方案 A：buildIndex 引用复用

**触发条件**：`sameRef = false` 或 `updateFieldConfig` 退化 > 1.2x。

**实施**：
- 检查步骤 2 伪代码 `buildIndex(draft.components, draft.byId)` 的第二参数是否传入
- 若 `draft.byId` 是 Immer Proxy（不生效），改用 `state.byId`（produce 第一个参数，原始未代理对象）
- 重新验证 `verifyImmerProxyReference`

**关联**：元计划 §5.3.4 + 决策 11 前置验证。

#### 4.4.2 方案 B：对齐操作批量 setComponents（步骤 2 配套必做项）

**定位**：**必做项，不是回退项**。基线已证明触发条件必然满足（N=10=3731ms >> 50ms，N=440=74933ms >> 200ms）。

**实施时机**：阶段 4 步骤 2 完成时同时实施，作为步骤 2 的补充 commit。

**实施**：
- 把 `canvas-graph/index.tsx` 的 `handleAlign` 从 N 次 `dispatch(updateFieldConfig(id, patch))` 改为 1 次 `dispatch(setComponents(newTree))`
- 在 `handleAlign` 内用 Immer produce 构建新 tree（统一改 N 个组件的 left/top）

**依据**：基线实测对齐批量 N=440 仅 523ms（vs 串行 74933ms），且与 N 无关。

**回退验证**（方案 B 实施后）：对齐批量 N=440 > 200ms → 考虑方案 C 或检查 produce 实现。

#### 4.4.3 方案 C：rAF 节流

**触发条件**：onResize 单次 > 1000ms 或帧率 < 45fps。

**实施**：
- 对 `designer-field/index.tsx onResize` 路径的 `setComponents` 加 `requestAnimationFrame` 节流
- throttle 内合并多次 resize（取最后一次参数，需设计合并策略）

**依据**：基线 onResize 单次 1139ms，5 秒仅触发 2 次（预期 50 次）——主线程被阻塞。rAF 节流可合并多次 resize 到 1 帧。

**注意**：基线已表明 onResize **当前就有问题**（非单源引入），此方案是顺带优化。

#### 4.4.4 方案 D：增量 buildIndex

**触发条件**：方案 A-C 都不达标。

**实施**：
- `buildIndex` 改为只重建被改节点 + 祖先链的 byId 条目，其余保留旧引用
- 复杂度从 O(n) 降到 O(depth)

**风险**：增量 buildIndex 实现复杂，可能引入新 bug。仅在方案 A-C 都不达标时考虑。

#### 4.4.5 方案 E：回退双源架构

**触发条件**：方案 A-D 都不达标。

**实施**：`git revert` 步骤 2/3/4/5（按 §5 回退依赖图顺序）。

**影响**：单源重构失败，回到双源架构。但 mutation 修复（步骤 1a）+ 死代码清理（步骤 6b/6c）+ 文档更新（步骤 7）可保留。
