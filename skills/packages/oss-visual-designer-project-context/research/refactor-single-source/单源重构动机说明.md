## 1. 一句话总结

task-006→012 的设计器状态重构引入了 byId / components 树双源写入机制，虽然达成了字段级订阅的性能目标，但引入了远超预期的维护复杂度和连环 bug。单源重构（components 树唯一真相，byId 纯派生）旨在从根本上消除双源同步问题。因改动范围大，先制定元计划把把握提到 9 成再动手。

## 3. 性能目标达成了吗

**达成了**。`useFieldConf` 字段级订阅确实减少了重渲染——拖动单个组件不再触发所有组件 re-render。这是真实的收益。

**量化说明**（基于 task-006→012 的设计目标与文档记录）：

- **拖拽场景 re-render 次数**：从"全量 440 组件 re-render"降到"仅被拖组件 1 次 re-render"（`useFieldConf(uniqueId)` 仅订阅 `byId[id]`，其他组件的订阅引用不变）
- **buildIndex 性能**：440 组件 1-2ms（[01-data-model.md §2](../design/src/designer-canvas/01-data-model.md) 记录）
- **字段级更新延迟**：从原 `useDebounceMergeConfig` 的 30ms debounce 延迟降到 0ms 同步 dispatch（task-008 删除 debounce）

> 注：当前没有保存拖拽帧率的量化测试报告（task-019 计划引入 vitest 后可补测）。但 task-006→012 的设计目标"字段级订阅减少重渲染"已通过 `useFieldConf` 的 shallowEqual 订阅机制达成，逻辑上成立。

> **性能基线缺失的风险**（单源重构前必须补）：由于当前没有量化基线，单源重构后无法对比"重构前 vs 重构后"的拖拽帧率/buildIndex 耗时。元计划 §5.3.1 已要求在重构前用 Performance API 实测当前双源架构的基线数据（buildIndex 耗时 / updateFieldConfig 总耗时 / 拖拽帧率 / CPU 占用），作为重构后验证的对比依据。

## 4. 维护代价是什么

**远超预期**。`updateFieldConfig` 只改 byId 不改树，导致 byId 和 components 树成为两个可独立写入的数据源。为了同步这两个源，引入了：

- `mergeByIdIntoTree`：三方向合并函数（`nodeWins` / `byIdWins` / `fieldPreserve`）
- `dirtyConfigKeys`：追踪哪些字段被字段级更新过
- `fieldPreserve`：第三种合并方向，用 dirtyConfigKeys 判断取值
- `beginSkipGroupRecalc` / `endSkipGroupRecalc`：跳过机制，绕过 recalcGroupBounds

### 4.1 连环 bug 时间线

```
updateFieldConfig 只改 byId（task-008，性能优化）
  → byId/树脱钩
  → mergeByIdIntoTree nodeWins 合并 → 改名丢失（task-012-3 验证已修）
  → 改合并方向为 fieldPreserve + dirtyConfigKeys（task-012-1）
  → fieldPreserve 覆盖归一化值 → 组位置漂移 + 二次位移（task-012-2 v1）
  → 修复 v1 引入新 bug：byId 与树长期不一致 → 选中跳回旧位置（task-012-2 v2）
  → 先 updateFieldConfig 再 setComponents 两步同步（task-012-2 v2 修复）
  → 组位置不跳变了，但暴露"组内对齐时 recalcGroupBounds 会跳组位置"
  → task-012-d 引入 beginSkipGroupRecalc/endSkipGroupRecalc 试图绕过 recalcGroupBounds
  → 实际无人调用（设计时漏掉了 handleAlign 是先 updateFieldConfig 改 left/top，
    而 recalcGroupBounds 监听 byId 引用变化，触发时机已经晚于 updateFieldConfig）
  → skip 机制沦为死代码（阶段 1 现状清单 §1.9 确认：beginSkip/endSkip 全 src 无调用方）
  → 现状：仍依赖 recalcGroupBounds + 两步同步，未真正解决根因
```

每个修复都暴露下一个。v1 修复甚至引入了新 bug。task-012-d 的 skip 机制更是直接沦为死代码——为绕过一个问题引入的补丁，连调用方都没接上，是"补丁套补丁"循环的典型案例。

### 4.2 还有未发现的潜在问题

在 task-012-2 分析中发现以下问题**尚未触发但潜在存在**：

| 问题 | 描述 | 触发条件 |
| --- | --- | --- |
| dirtyConfigKeys 永远只增不减 | `buildIndex` 重置，但连续字段级更新不触发 setComponents 时持续累积 | 连续拖动多个组件 + 改名，中间无结构性操作 |
| ~~undo/redo 未验证~~ | ~~`fieldPreserve` + `dirtyConfigKeys` 完全没考虑 undo/redo~~ | ~~用户拖动 → undo~~ |
| 并发 dispatch 时序 | recalcGroupBounds 两次独立 dispatch 中间可能插入其他 action | React 批量更新中断 |
| 内存泄漏 | dirtyConfigKeys 是 Set，挂在 byId 的 FlatField 上，组件删除后可能不清理 | 组件删除 |

> **2026-07-27 修正**：阶段 1 现状清单 §1.16 已确认 **undo/redo 是完全未实现的死字段**——reducer 只有 `undo: []` / `redo: []` 字段定义，无任何 action 读写；toolbar 唯一清空 undo/redo 的 `handleClear` 函数被注释掉；无撤销/重做按钮、无 pushUndo 逻辑。因此"undo/redo 未验证"这一潜在问题**实际不存在**（根本未实现），单源重构不需要考虑 undo/redo 兼容性。此行保留作为历史记录，实际风险已消除。

## 5. 根本原因

**双源写入**。byId 既是"派生索引"（从树 build），又是"可独立写入的缓存"（updateFieldConfig）。一旦 byId 能被独立写入，它就和树脱钩了，于是需要合并机制来"重新同步"——而同步逻辑的每个分支都可能是 bug。

这不是某个具体实现的错误，而是**架构决策的衍生代价**。task-008 选择"只改 byId 不改树"是为了避免每次拖拽都 produce 整棵树，但这个性能优化引入了双源同步的复杂度，而复杂度的代价（4 个已发 bug + 4 个潜在 bug + 3000 行文档 + 2 个测试 task）已经超过了性能收益。

## 6. 为什么不继续打补丁

当前已进入"补丁套补丁"循环：每个补丁修补双源同步的一个边角，但双源同步本身就不该存在。继续打补丁的预期结果：

- 修 dirtyConfigKeys 累积 → 可能引入"该保留的字段没保留"
- 修 undo/redo → 可能引入"undo 后 dirtyConfigKeys 状态错误"
- 修并发 dispatch → 需要引入事务机制，复杂度再上一个台阶

**每个补丁都在增加而不是减少复杂度**。

## 7. 单源重构是什么

components 树作为唯一真相源，byId 纯派生不可独立写入：

```
当前（双源）：                目标（单源）：
                              
updateFieldConfig             updateFieldConfig
  → 只改 byId                   → Immer produce 改树（结构共享 O(depth)）
  → 树不变（stale）             → buildIndex 从树派生 byId
  → setComponents 时合并        → 无需合并
                              
setComponents                 setComponents
  → mergeByIdIntoTree 合并      → buildIndex 重建（无合并）
  → 三方向 + dirtyConfigKeys    
                              
getSaveableComponents         getSaveableComponents
  → byIdWins 合并               → 直接序列化树
```

### 7.1 能删除什么

- `mergeByIdIntoTree` 三方向（nodeWins / byIdWins / fieldPreserve）
- `dirtyConfigKeys`
- `fieldPreserve` / `nodeWins` / `byIdWins`
- `recalcGroupBounds` 的两步同步（简化为单次 setComponents）
- `safeReadChildNodes` / `safeReadFieldConf`（task-015 计划的，不再需要）
- `beginSkipGroupRecalc` / `endSkipGroupRecalc`（可能不再需要）

### 7.2 性能影响

| 操作 | 当前（双源） | 目标（单源） | 差异 |
| --- | --- | --- | --- |
| updateFieldConfig | O(1) 改 byId | O(depth) produce + O(n) buildIndex | 多了 O(n) |
| setComponents | O(n) mergeByIdIntoTree | O(n) buildIndex（无合并） | 持平 |
| useFieldConf 订阅 | O(1) 读 byId | O(1) 读 byId（派生的） | 不变 |

**关键**：buildIndex 在 440 组件下 1-2ms，Immer produce 做结构共享（改叶子只复制路径），React 渲染开销远大于此。性能影响可接受。

## 8. 为什么要做元计划而不是直接重构

task-006→012 的教训：**没有充分分析就动手，导致连环 bug**。单源重构影响 17+ 个 `updateFieldConfig` 调用方、reducer 核心、保存路径、组尺寸重算——比之前任何一次改动都大。

元计划（task-2026-07-27-001）定义 6 个阶段，每阶段完成后暂停 review，确保方案做到 9 成把握再动手。核心原则：

- **先摸清现状再定目标**：阶段 1 全面摸清代码 + 文档，不留盲区
- **先分析差距再定步骤**：阶段 3 列出每个文件的改动 + 风险
- **先定验证再动手**：阶段 5 定义"怎么确认没问题"
- **每步可回退**：阶段 4 拆成可独立 commit + revert 的步骤

## 9. 文档问题

designer-canvas 目录 9 个文件共约 3000 行，又厚又难维护。根因是双源同步机制本身复杂，需要大量文档解释三种合并方向、dirtyConfigKeys 生命周期、stale tree 防护、边界场景。

单源重构后，这些内容的大部分会过时或删除（02-write-path 约 1/3、04-edge-cases 约 1/2、05-known-bugs 约 1/2）。重构后文档会大幅精简。

## 10. 结论

| 维度 | 当前（双源） | 目标（单源） |
| --- | --- | --- |
| 性能 | ✅ 字段级订阅 | ✅ 持平（buildIndex 1-2ms 可接受） |
| 维护 | ❌ 3000 行文档 + 连环 bug | ✅ 删除合并机制，文档大幅精简 |
| 可预测性 | ❌ 4 个已发 bug + 4 个潜在 bug | ✅ 单一真相源，无双源同步问题 |
| 扩展性 | ❌ 每个新场景都要考虑双源 | ✅ 只改树，byId 自动派生 |

### 10.1 风险与缓解

单源重构并非零风险，以下是已识别的风险及缓解措施（阶段 2 决策时需深入评估）：

| 维度 | 风险 | 缓解 |
| --- | --- | --- |
| 性能 | `updateFieldConfig` 从 O(1) patch byId 变为 O(depth) Immer produce 改树 + O(n) buildIndex | 440 组件场景实测（buildIndex 1-2ms，Immer 结构共享只复制路径，React 渲染开销远大于此）；若不达标可考虑增量 buildIndex |
| 兼容性 | 第三方物料或微应用直接读 `byId[id]` | 保持 `byId` 接口不变（仍为 `Record<string, FlatField>`），只是来源从"双源写入"变"纯派生"——调用方零感知 |
| 撤销栈 | ~~撤销/重做可能与新架构不兼容~~ | ~~阶段 2 摸清 undo/redo reducer 后单独评估~~ → **2026-07-27 确认：undo/redo 是死字段，未实现，无兼容性风险**（见 §4.2 修正） |
| 回归 | 已修 bug（改名丢失 / 位置漂移 / 保存丢失）可能复现 | 阶段 5 验证方案：task-012-4/012-5 测试 + 浏览器冒烟清单 + 440 组件性能验证 + git revert 回退路径 |
| 文档 | 3000 行文档需同步更新 | 阶段 1 现状清单 §2 已标注每份文档的删除/重写比例，阶段 4 拆分文档更新为独立步骤 |

**单源重构不是否定 task-006→012 的工作**——字段级订阅（useFieldConf）、Redux 迁移、不可变改造都是有价值的。只是 `updateFieldConfig` 只改 byId 不改树这个具体决策引入了不可控的复杂度，需要修正。

元计划的目标是把这个修正做到 9 成把握。
