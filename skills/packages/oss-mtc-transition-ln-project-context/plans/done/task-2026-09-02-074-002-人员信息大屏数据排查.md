## 3. 排查记录

### 3.1 模块1 退役军人构成（retired-soldier / RetireePieCard）：3 分类全 0 ✅ 已修复（2026-09-03）

**现象**：省级默认 3 个分类（退役军官/军士/义务兵）全 0。

**根因**：`stats_jdlk_persion_infor_cant` 的 `PROVINCE_CODE` 实际长度随层级变化——省 2 位（`21`）/ 市 4 位（`2101`）/ 区县 6 位（`210102`）；前端地图派发 ECharts 标准 6 位 adcode（`210000`/`210100`/`210102`），`veteran.sql` 等值匹配落空。

**修复**（`backend/app/services/visual/big_screen/personnel.py`）：

- 新增 `_infor_cant_code()`：6 位 adcode 按层级截短（`210000`→`21`，`210100`→`2101`，区县原样）；非 6 位入参原样返回
- `_fetch_category` 加 `normalize` 开关，**仅 veteran 启用**（preferential 的表 `abi_zb_tyjrjqyfdx` 码约定不同：省 `2101`/市 `210100`，其 SQL 已自行兼容省码，不能共用归一化）
- `_fetch_total_row`（模块2 total，同表同约定）同步接入归一化

**验证**（直调 service）：省/市/区县 3 层 + 旧 2/4 位入参回归全部正确——
`210000`→180158/148226/1277393（与 `21` 一致）；`210100`→55385/33524/225946（与 `2101` 一致）；`210102`/`210124` 有数；模块2 total 同步恢复。

### 3.2 模块2 下钻 /total/detail：全分类子集全 0 ✅ 已修复（2026-09-03）

**现象**：`big-screen/personnel/total/detail` 下钻结果全部为 0。

**根因**（与 §3.1 同族但不同表）：`abi_zb_tyjrjqyfdx` 表内**只有 4 位市级行（2101~2115）**，无省级汇总行 `21`；前端 6 位 adcode（`210000`/`210100`）也等值匹配不上 4 位码。

**修复**：

- service 新增 `_tyjrjqyfdx_cant_pattern()`：`210000`/`21` → LIKE `'21%'`（全省 SUM 15 市）；`210100`/`210102`（市/区县）→ `'2101'`（截 4 位，表无区县行）
- [total_detail.sql](backend/app/repositories/sql/visual/big_screen/personnel/total_detail.sql) 改为 `WHERE cant_code LIKE` + service 每列拼 `SUM(col)`（省级聚合多行）
- 踩坑 2 个：① psycopg2 会扫描 SQL **注释**里的 `%` 字符，注释写 `'21%'` 会报 `argument formats can't be mixed`——注释中避免裸 `%`；② SQL 模板外层不能留 `SUM()`，否则与 service 拼的 `SUM(col)` 套成 `SUM(SUM(...))`

**验证**：`210000` 与 `21` 一致（officer 567,000 / sergeant 479,124，15 市 SUM）；`210100` 与 `2101` 一致（168,144 / 101,187）；4 类 category 全测通过。

### 3.3 口径修复：模块2 顶层与下钻数值不一致（180,158 vs 567,000）✅ 已修复（2026-09-03）

**现象**：用户反馈——顶层退役军官 180,158，但 `/total/detail?cantCode=210000&category=officer` 各分类之和 567,000。

**根因（两层）**：

1. **快照重复计数**：`abi_zb_tyjrjqyfdx` 是**每日快照表**（同一 cant_code 每天 1 行，insert_time 08-23~26 共 3~4 天），§3.2 的 SUM 把多天全加了（567,000 ≈ 3 × 189,000）。08-23 只有部分市有数据（全省 officer 仅 21,289）
2. **两表数据本身不一致**：`abi_zb` 最新快照（08-26）officer=181,900，`stats_jdlk_persion_infor_cant`=180,158，差 1,742（约 1%）。而 detail 的子分类字段**只存在于 abi_zb**，顶层却查 infor_cant，跨表无法对齐

**修复**（保证「顶层 = 下钻之和」）：

- [total.sql](backend/app/repositories/sql/visual/big_screen/personnel/total.sql) 数据源从 `stats_jdlk_persion_infor_cant` 切换为 `abi_zb_tyjrjqyfdx` **最新快照**（`insert_time = 全局 MAX`），用表内合计列 `tyjrhj/tyjghj/tyjshj/tyywbhj/yfdydxhj`
- [total_detail.sql](backend/app/repositories/sql/visual/big_screen/personnel/total_detail.sql) 同步加最新快照过滤
- `_fetch_total_row` 参数归一化从 `_infor_cant_code` 改为 `_tyjrjqyfdx_cant_pattern`（同源同码）

**验证**（省/市/区县 × 4 category 全对齐）：省级 officer 181,900 / sergeant 149,147 / conscripts 1,285,112 / catPreObject 17,172，**顶层 = 下钻合计逐项相等**；沈阳级 56,046 / 33,731 / 227,647 / 3,365 同样一致。

**遗留口径差异（待用户拍板）**：模块1 退役军人饼图仍用 `stats_jdlk_persion_infor_cant`（180,158），与模块2（181,900）差 1,742（约 1%）——两张源表数据本身不一致，非代码问题。若要求模块1 与模块2 同口径，需把 veteran 饼图也切到 abi_zb（其表内无 officer/sergeant/conscripts 三分类的直接列？待查 tyjghj/tyjshj/tyywbhj 即为三分类合计，**可切**）。

**坑（第 3 次踩）**：SQL 注释里的 `%` 又触发 psycopg2 `dict is not a sequence`（「约 1% 差异」）——**规则：SQL 文件注释禁用 `%` 字符**。

### 3.4 对照 038 spec 核查：沈抚新区 2115 合并规则遗漏 ✅ 已补（2026-09-03）

**背景**：用户指示对照 `docs/specs/038-bigdata-personnel-display`（spec §11.3 D-3、data-model-extensions §4.1/§4.5）核查 §3.1~§3.3 的修复是否合规。

**发现**：spec §4.5 规定「辽宁省沈抚新区 | 4 | 2115（合并到 2104 抚顺市）」，§4.1 明确「抽出 2115 行与 2104 抚顺市数值相加，移除沈抚新区独立行」。而 §3.1~§3.3 的实现均未做这层合并。实测两张表都有独立 2115 行（abi：2104×3 行 + 2115×4 行；infor_cant：抚顺 75,351 / 沈抚 1,481）。

**修复**（`personnel.py` + 3 个 SQL）：

- `_infor_cant_code` → `_infor_cant_codes`（返回列表）：抚顺 `2104` → `['2104','2115']`
- `_tyjrjqyfdx_cant_pattern` → `_tyjrjqyfdx_cant_patterns`（返回列表）：抚顺（含 6 位 adcode `2104xx` 区县下钻）→ `['2104','2115']`
- `total.sql` / `total_detail.sql`：`LIKE %(cant_code)s` → `LIKE ANY(%(patterns)s)`；`veteran.sql`：`= %(cant_code)s` → `= ANY(%(cant_codes)s)`
- `_fetch_category` normalize 分支改传 `cant_codes` 列表

**验证**（`_tmp_check_sf.py` 已删）：

- infor_cant veteran 抚顺（含沈抚）= 76,832 = 75,351 + 1,481，合并精确
- abi total 抚顺 veteran 76,955（含 2115 行），全省 1,616,159
- 6 位区县码 `210402`（顺城区）下钻也正确归并到抚顺市口径

**注意**：省码 `210000` 模式 `['21%']` 天然涵盖 2115，全省数值不受影响；此前 §3.1~§3.3 的省/市验证结论中，**仅抚顺市一档此前偏小**（漏加 2115 行），其余地市不受影响。
