## 0.9 同根 bug：city 级 14 市全 0 空数据（2026-09-02 发现并修复）

> 本 task 调研启动后，**先撞上的是 city 级 bug**（rank city 级「14 市全 0」），与本 task 「district 级过滤」是**同一根因**的两个层级表现。先修 city 级，再做 district 级客户端过滤。

### 现象

调用 `GET /api/visual/big-screen/petition-comparison/rank?organId=210100`：

- SQL 实际返回 **14 行**沈阳区/县数据（`cant_code` 9 位如 `210102000`）
- Service 处理后 14 个市 `num` 全部 0
- 返回 `{local:{regions:[]}, beijing:{regions:[]}}`（空态）
- rank 端点对**所有 14 市永远返回空数据**

### Root cause（两个 bug 叠加）

**Bug 1：CANT_CODE 长度不匹配（字符串 `startswith` 语义陷阱）**

- DB 返回 `cant_code` 是 **9 位区划码**（如 `'210102000'` = 沈阳市和平区）
- `_RANK_CITIES` 用 **6 位市码**（如 `'210100'`）
- 原匹配：`r["cant_code"].startswith(code)`
    - `'210102000'.startswith('210100')` → **False**（9 位码前 6 位是 `'210102'`，不是 `'210100'`）
- `startswith` 是**完整字符串前缀匹配**，不会按数字位前缀匹配
- 结果：14 个区/县**一行都匹配不上** → 14 个市全 0

**Bug 2：同市多行只取第一行（即便匹配上也错）**

- 原 `next()` 只取**第一个匹配行**
- SQL 未 `GROUP BY`，每区/县一行（沈阳市 14 区/县 = 14 行）
- 第一个匹配行：`cant_name='沈阳市经济技术开发区' cant_code='210199000' num=None`
- `_to_int(None)` 返回 0 → 沈阳市 num 还是 0

### 修复（已落到代码，commit 前待 review）

`backend/app/services/visual/big_screen/petition_comparison.py#L478-L505` `_fill_rank_city_full_set`：

```python
matched_regions = [
    r for r in regions
    if r["cant_code"][:4] == code[:4] or r["cant_name"] == name
]
if matched_regions:
    total_num = sum(r["num"] for r in matched_regions)
    max_time = next(
        (r["max_time"] for r in matched_regions if r["max_time"]),
        "",
    )
    filled.append({
        "cant_name": name, "cant_code": code,
        "num": total_num, "max_time": max_time,
    })
else:
    filled.append({"cant_name": name, "cant_code": code, "num": 0, "max_time": ""})
```

- 匹配改用**前 4 位匹配市级码前 4 位**（兼容 9 位区划码：沈阳下辖区/县 `2101xx000` 前 4 位都是 `2101`）
- **SUM** 所有匹配行，不再 `next()` 只取首行
- `max_time` 取第一个非空值

预期：沈阳市 `local ≈ 2148`（14 区/县 SUM）、`beijing ≈ 571`；其他 13 市 `NUM=0`（因 organId=210100 只查沈阳，级联不到其他市）。

## 0.10 文档层根因分析：4 层假设断裂

> bug 表面是代码错，**深层是 4 层文档/设计各自"对了一部分"，但跨层契约缺失**。值得单独立项，避免其他模块再踩。

### 4 层假设断裂示意

| 层                | 文件 / 章节                                     | 假设                                   | 真相                                                      |
| ----------------- | ----------------------------------------------- | -------------------------------------- | --------------------------------------------------------- |
| ① PM 输入 SQL     | `pm-inputs/assets/...txt` §地区排名             | "每市 1 行"（隐含，无 `GROUP BY`）     | 实库是"每**区/县** 1 行"（沈阳 14 区/县 = 14 行）         |
| ② 数据模型        | `data-models.md` §7.6 `letter_screen_5`         | "CANT_CODE varchar(32) 区划代码"       | 没说实库是 **9 位**（区/县级如 `210102000`）              |
| ③ API 契约 + spec | `api-contracts.md` §7.44 + `spec.md` §3.3 模块5 | "兼容 6/12 位区划码"                   | 含糊承诺，没说怎么兼容；实际 DB 是 9 位（既非 6 也非 12） |
| ④ Service 实现    | `_fill_rank_city_full_set`                      | `startswith(6位市码)` 应能匹配 9/12 位 | 字符串前缀 ≠ 数字位前缀；`startswith` 不补位不模糊匹配    |

### 失败点归类

| 类型     | 失败点                                                                         |
| -------- | ------------------------------------------------------------------------------ |
| 文档遗漏 | `data-models.md` §7.6 未标 `CANT_CODE` 实际长度（9 位）                        |
| 文档含糊 | `api-contracts.md` + `spec.md` 「兼容 6/12 位」未细化匹配算法                  |
| 设计缺陷 | SQL 模板不 `GROUP BY`，隐含「每市 1 行」错误假设                               |
| 实现错误 | `startswith(6位)` 错配 9 位区/县码；`next()` 只取首行丢数据                    |
| 流程缺失 | acceptance-tests.md 只跑 mock，无真实 DB 验证；「全 0 空数据」bug 一路活到联调 |

### 关键模糊点：「兼容 6/12 位区划码」

实现者看到这句话时，自然理解为「`startswith(6位市码)` 能搞定 12 位」：

- 12 位乡/村级码 `210102000000`：`startswith('210100')` → **False**（同样问题）
- 9 位区/县级码 `210102000`：`startswith('210100')` → **False**（同样问题）

但实现者**没意识到 DB 实际是 9 位**——因为② 没标长度。以为"6 位市码 startswith 应该能匹配 9/12 位"，结果**实测**才暴露。

### 文档补全清单（4 处，待 PR 走 L3 严控）

1. **`data-models.md` §7.6**：补"`CANT_CODE` 实库为 **9 位**区/县码（如 `210102000` = 沈阳市和平区）；与 6 位市级码的对应通过**前 4 位前缀**匹配"
2. **`api-contracts.md` + `spec.md`**：把含糊的「兼容 6/12 位区划码」改成明确的「`CANT_CODE` 9 位，与 6 位市码按**前 4 位**匹配；同市多区/县行需 **SUM**」
3. **SQL 模板 `rank.sql`**：**降级为「可选优化」**——本 task 通过 Service 层 `[:4] + SUM` 兼容，不阻塞；后续如要"防 SQL 层脏数据"再考虑加 `GROUP BY`
4. **`acceptance-tests.md`**：加真实 DB 数据驱动用例（orgin_id=210100 → 沈阳 14 行；orgin_id=210000 → 全省 14 市至少各有 1 行；orgin_id=210124 → 1 行（district 级映射父级市后过滤）；空数据场景 → 空态契约触发）
