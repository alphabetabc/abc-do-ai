## 0.1 Bug 详情

- **现象**：大屏接口（人员 / 辽宁信访 / 进京信访）在 API 无业务数据或请求失败时，`request.ts` 拦截器会注入前端内置 mock 数值（人员总数、地市分布等硬编码数据），导致生产环境大屏展示伪造数据
- **复现步骤**：当 `isPetitionUrl` 匹配的接口返回 200 但 `data` 为空，或请求失败（非 401）时，触发 `buildPetitionMockResponse` → 调用 `resolvePersonnelMock` / `resolveBeijingPetitionMock` / `resolvePetitionMock` → 返回硬编码数值
- **期望行为**：可通过开关控制是否启用 mock 兜底，生产环境关闭后兜底返回空数据
- **实际行为**：兜底逻辑硬编码注入 mock，无任何开关控制
- **涉及模块 / 路由**：`/visual/big-screen?menu=personnel` / `?menu=petition` / `?menu=beijingPetition`
- **首次发现时间 / 版本**：2026-09-02

## 0.3 联调发现 / 修复的二级 Bug

实施步骤 8 后，联调发现并修复了 3 个二级 bug，均未走单独 task：

### 0.3.1 二级 Bug #1：`syncRegion` 手动 pick 丢失 `parentCity`

- **现象**：039 / 040 双击区县后，柱图仍按省级兜底返回空数据（cantCode 为空，SQL 走省级兜底）
- **根因**：`petition-map-overview` 的 `syncRegion` 函数手动 pick 了 `adcode/name/level` 三个字段，**丢弃了 `parentCity`**
- **影响范围**：039 / 040（038 用 `dispatch(region)` 直接传 object，无此问题）
- **修复**：`syncRegion` 改为条件性携带 `parentCity`
    ```typescript
    dispatch(..., {
        adcode: region.adcode,
        name: region.name,
        level: region.level,
        ...(region.parentCity ? { parentCity: region.parentCity } : {}),
    } as Region);
    ```
- **反思**：未来 store / Region 类型新增字段时，需同步检查所有 `syncRegion` 类封装函数，避免再次丢失

### 0.3.2 二级 Bug #2：district 级 9 位 vs 6 位 adcode 比较失败

- **现象**：district 级客户端过滤 `String(it.adcode) === selfAdcode` 永远 false，结果被全部过滤掉
- **根因**：后端 `letter_screen_5` 库里 `CANT_CODE` 实测为 9 位（如 `210102000`），`region.adcode` 是 6 位（如 `210102`），直接比较不一致
- **调研结论**：
    - 4 个后端 service 对**入参**都有归一化（`SUBSTR`/`IN (code, code\|\|'000')`/`ljust(9, '0')`）
    - 4 个 service 对**出参 `adcode`** 全部原样返回，**未归一化**
    - 数据契约不规范，属于「设计债」而非后端 bug
- **修复**：038 / 039 / 040 客户端过滤统一加 `.slice(0, 6)` 截断比较；041 之前已有 `r.cantCode.slice(0, 6)` 处理
- **后续可优化（未在本 task 范围）**：建议后端在 service 层统一 `adcode = str(code)[:6]` 返回，避免每个前端组件重复 `.slice(0, 6)`

### 0.3.3 重构：IIFE → `useMemo`

- **原代码**：3 处 `const cantCode = (() => {...})()` 自执行函数
- **改为**：`useMemo(() => {...}, [region])`
- **原因**：IIFE 每次 render 都重算；`useMemo` 依赖未变时复用，代码库惯用写法
- **影响文件**：038 / 039 / 040 共 3 个柱图组件
