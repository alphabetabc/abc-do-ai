## 1. 设计定稿（2026-09-03 用户拍板）

### 1.1 背景

大屏是 7×24 挂屏展示端，当前各模块数据仅在挂载 / 联动参数变化时拉取一次，数据更新后大屏展示过期数据。

### 1.2 方案：1 小时固定轮询 + 双轨接入 + 分批执行（定稿）

**每小时轮询一次**。固定轮询天然覆盖所有过期场景（跨天、休眠恢复、后端数据更新）。仓库存在两种请求模式，按模式分别接入，**不**借机统一迁移：

- **041 比对大屏**（已是 `useRequest`）：直接追加 `pollingInterval`
- **038/039/040**（手写 `useEffect`，15 个组件）：新增共享 `usePolling` hook 接入

> 方案取舍（2026-09-03）：曾评估「统一迁移 useRequest」，回归风险高，用户拍板选风险更小的 usePolling 包一层。统一迁移留作未来独立 task。

> **分批执行（2026-09-03 用户拍板）**：15 个文件一次性改动副作用太大，本 task 按 §2 的批次执行，**每批完成后人工冒烟验证通过才进下一批**，任何一批出问题可单独回滚，不影响已验证批次。

### 1.3 `usePolling` hook 设计

```ts
/**
 * 大屏数据轮询 hook。
 * - 每小时调用一次 fn（默认 BIG_SCREEN_POLLING_INTERVAL = 3_600_000）
 * - 组件卸载自动清理定时器（fn 内的 cancelled 标志由本 hook 机制替代）
 * - fn 引用变化（联动参数更新 useCallback）时重置计时，避免旧参数轮询
 * - 立即调用首帧不在此 hook 职责内（首拉仍由原 useEffect / useRequest 负责，职责单一）
 */
function usePolling(fn: () => void, intervalMs: number = BIG_SCREEN_POLLING_INTERVAL): void;
```

useEffect 模块接入方式（纯请求组件，每模块约 3 行）：

```tsx
// 现有请求体抽成 useCallback（依赖数组 = 原 useEffect 依赖）
const fetchData = useCallback(() => {
    /* 原 useEffect 内逻辑（去掉 cancelled 标志） */
}, [cantCode]);
usePolling(fetchData);
// 原 useEffect(() => { fetchData(); }, [fetchData]) 保留，保证首拉 / 联动刷新不变
```

### 1.4 15 个组件通读结论（2026-09-03 已逐一核查，分三类）

#### A 类：纯请求组件，可直接机械抽取（12 个）

数据 effect 内只有 setLoading/setError/setData，幂等 GET，依赖数组明确：

| 组件（039 petition / 040 beijing-petition 同名镜像，代码逐行一致） | 原依赖数组                                                       | state 模式                       |
| ------------------------------------------------------------------ | ---------------------------------------------------------------- | -------------------------------- |
| identity-type ×2                                                   | `[currentRegion]`                                                | items/loading/error + DataStatus |
| channel-stat ×2                                                    | `[currentRegion?.adcode]`                                        | data/loading/error + DataStatus  |
| petition-demands ×2                                                | `[]`                                                             | data/loading/error + DataStatus  |
| petition-trend ×2                                                  | `[]`                                                             | items/loading/error + DataStatus |
| petition-region-bar ×2                                             | `[cantCode, region?.level, region?.adcode]`（含 eslint-disable） | items/loading/error + DataStatus |
| beijing-summary/overview-indicator ×2                              | `[]`                                                             | ⚠️ 见 C-2 前置修复               |

#### B 类：需拆分才能轮询（2 个：039/040 petition-map-overview 地图）

- 初始化 effect 混有副作用：`stackRef.current = [省帧]`（重置下钻栈）、`setCurrentAdcode('210000')`、`syncRegion(PROVINCE)`（dispatch 全局 interaction-store）——**这些行绝不能进轮询 fn**
- 轮询 fn 只做「按当前栈顶 cantType/cantCode 重取 mapData」，需参数化读栈顶（顺带修复 fetchMap 闭包读 `currentAdcode` state 但依赖为 `[]` 的 stale closure 问题）
- 该组件**无 loading/error/DataStatus**，catch 静默 `setMapData([])`；轮询失败页面会直接空白，需补 catch 兜底
- fetchMap 已是 useCallback（唯一已抽出的）

#### C 类：部分可轮询（1 个：038 personnel/data-overview）

- 3 个 effect：#1 初始 dispatch 省级默认区域（副作用）、#2 数据请求（可轮询）、#3 onApiChange 暴露 API（副作用）——仅 #2 进轮询
- **无 error 处理**（无 catch），轮询失败会无限 loading，需补 catch
- effect #2 的过滤依赖 `mapAdcode` 但未列入依赖（exhaustive-deps 被 disable），抽 useCallback 时须补齐

#### 前置修复项（接入前处理，避免轮询放大缺陷）

### 1.5 其他实现要点

1. **共享常量**：`BIG_SCREEN_POLLING_INTERVAL = 3_600_000`（1h），随 `use-polling/index.ts` 导出
2. **041 侧 loading 行为**：`useRequest` 轮询时默认不置 `loading=true`，图表不闪烁
3. **量级**：每屏 ≤7 模块 × 1 次/小时，Kingbase 压力可忽略
4. **不做什么**：不改后端；不改 `visual/stats/*`；不做分钟级轮询；不统一迁移 useRequest；**不**修改各组件的三态 JSX 消费方式（除 C-2 必要修复）
