# 005 · 大屏开发通用工作流

> 性质：长期维护文档（非一次性 research）
> 日期：2026-08-13
> 来源：领导指示——大屏开发需自顶向下设计，总结通用工作流
> 维护规则：工作流变化时同步更新；本文件不入 `docs/`、不入 Git；成熟后走 L3 审批落地到 `docs/workflows/`
> 首批验证案例：038-041 四个大屏

---

## 0. 定位

本文档定义大屏开发的**通用步骤**，适用于所有数据可视化大屏。

与现有文档的关系：

- `001-big-screen-dev-guide.md`：管「怎么用 docs 体系开展大屏任务」（12 步骤，偏文档流程）
- `004-big-screen-architecture.md`：管「大屏架构本身怎么设计」（布局/数据结构/组件/联动）
- **本文**：管「大屏开发从 0 到交付的推进顺序和依赖关系」（偏工程节奏）

> 001 的 12 步骤是文档层面（建 spec、迁 PM input、登记 design 等）；本文是工程层面（架构 → 组件 → 后端 → 前端 → 联调），两者互补。

## 2. 通用步骤

### 第一步：架构设计

**目标**：产出一个大屏架构母文档，定义所有大屏的共性约定。

**产出**：

- 布局模型（壳 + 槽位协议）
- 图表数据结构（统一 API 响应模型）
- 共享组件契约
- 交互联动协议
- 多屏共享与差异矩阵

**规则**：一次设计、多屏复用。后续新大屏只需在差异矩阵里补一行，不需重新设计架构。

**参考**：`004-big-screen-architecture.md`

> **时机**：首批大屏开发前做一次；后续新大屏只需检查架构文档是否需要扩展，不重复此步。

---

### 第二步：PM input 迁入 + 五件套生成

**目标**：每个大屏的需求输入结构化，生成 spec 五件套。

**产出**：

- `docs/specs/NNN-*/pm-inputs/`（assets + pm-requirements-input.md）
- 五件套：spec.md / plan.md / tasks.md / data-model-extensions.md / acceptance-tests.md

**依赖**：第一步架构文档定稿（spec §4 引用架构文档，不重复描述布局壳和组件协议）。

**规则**：

- PM input 的 A-K 章节结构保持统一
- 跨屏共享信息（布局/导航/地图/沈抚合并）在架构文档里统一记录，PM input 只写各屏差异
- spec §3 接口契约的 `data` 结构引用架构文档 §2 图表数据结构

> **时机**：每个大屏独立进行，PM input 就绪后即可启动。

---

### 第三步：共享组件 spec 生成 + 开发

**目标**：基于架构文档的组件契约，生成共享组件 spec 并实现共享组件。

**产出**：

- 共享组件 spec（`docs/specs/NNN-components-common/`，三件套：spec.md + task.md + data-model.md）
- 组件设计文档（`design/components/NNN-*/`）
- 组件代码（`frontend/src/components/large-screen/`）

**依赖**：第一步架构文档 §3 组件契约。

**规则**：

- 识别方式：AI 识别 + 人确认（见 004 §4.1）
- 首批大屏时做，后续大屏直接复用
- 与后端开发并行，互不阻塞
- 组件设计文档先在 skill `design/components/` 下起草，成熟后走 L3 审批落地到 `docs/design/`
- 组件 task 完成后回 004 §3.1 登记组件索引

> **时机**：首批大屏前端开发前必须完成；后续大屏只需检查是否需要新增组件。

---

### 第四步：后端开发（M1 竖切 + M2 批量）

**目标**：实现大屏后端 API。

**M1 竖切**：

- 公共 Service（cantCode 参数处理、占比计算、沈抚合并）
- 首个端点完整实现（SQL + Service + router + schema + 鉴权 + 合同测试）
- 验证公共逻辑可复用

**M2 批量**：

- 其余端点复制 M1 模式
- SQL + schema + router + 合同测试

**依赖**：

- 第二步五件套的 `data-model-extensions.md`（SQL 字段映射）
- 第一步架构文档 §2 图表数据结构（API 响应模型）
- 数据库表已建 + 可读（数据可后导入，不阻塞 SQL 编写）

**规则**：

- 与第三步公共组件开发并行
- 运行时 SQL 不入 migration，放 `backend/app/repositories/sql/visual/`
- 端点前缀无 `/v1`，用 `/api/visual/big-screen/{screen}/{module}`
- **编码前实库核实**（041 O-2 经验）：写 SQL 前先用 information_schema 直查核对该表实际字段名/类型/长度，与 data-models 比对；差异（如 ORGAN_ID 实为 9 位、字典码列实存）记入 spec §10 并调整口径，**不臆造字段**

> **时机**：五件套生成 + 架构文档定稿后即可启动，不依赖前端。

---

### 第五步：前端开发（M3 壳+首模块 → M4 其余模块）

> **2026-08-17 更新（task-041 经验）**：M3 在实战中发现需要先确定**路由方案**（单路由 + query vs 多路由 + Outlet）和**大屏壳形态**（独立 `Visual` 壳 vs `BigScreenShell` + Outlet）。

**M3**：

- **路由方案决策**：单路由 `visual/big-screen` + `?menu=xxx` query 切换（task-041 验证可行；保留 tab 体系 + 防止重复创建）；`Visual` 壳替代原计划的 `BigScreenShell`
- 大屏入口页（`Visual`）+ 公共壳（`Header` 导航 + `Background` 背景 + `ScalerContainer`）
- 大屏子页（每个屏的 `index.tsx`）：主入口仅做组合（`import` 各业务子组件 + 渲染）
- 业务子组件初始化（每个卡片一个 `kebab-case` 目录 + `index.tsx`，InfoCard 绝对定位）
- API 封装（待后端 M1 完成）
- 首个模块实现（验证视觉 + 交互 + 公共组件可用性）
- 地图模块（如该屏有地图）

**M4**：

- 其余模块批量实现
- 地图下钻联动（全局刷新）
- 指标下钻（局部替换）
- 加载态 / 空态 / 错误态

**依赖**：

- 第三步公共组件就绪
- 第四步 M1 API 就绪（M3 至少需要一个端点联调）
- geojson 文件就绪（地图模块）

**规则**：

- M3 先做一个模块 + 壳，视觉定稿后再批量
- 图表组件统一接收架构文档 §2 定义的数据结构作为 props
- 业务子组件**自包含**：`position: absolute` + 像素坐标 + InfoCard props 内联在子组件内，主入口不写定位
- 卡片参数（width/height/left/top/titleBg）须沉淀到 task 文件（如 task-041 §0.3.x）

> **时机**：公共组件 + M1 API 就绪后启动。**M3 路由方案决策必须先于 M3 编码**。

---

### 第六步：联调验收（M5）

**目标**：全模块联调，与 PM 截图对数，验收通过。

**产出**：

- 与 PM 截图对数（省级 + 市级视图）
- 401/403 全端点测试
- acceptance-tests P0 场景自动化
- 沈抚合并边界验证
- 地图下钻响应时间 ≤ 3s
- 图表 + 地图性能验证

**依赖**：M4 全模块完成。

**规则**：

- 验收通过后更新 AGENTS.md §2.1 模块表 + specs/index.md 状态列
- 公共组件和模式此时得到验证，可供后续大屏复用

> **时机**：M4 完成后启动。

---

### 第七步：后续大屏复制

**目标**：复用已验证的公共组件、后端模式、前端模式，高效开发后续大屏。

**依赖**：

- 首批大屏（038）M4 跑通
- 公共组件和模式已验证
- 后续大屏的 PM input 已就绪

**流程**：

- 从第二步开始（PM input 已就绪则直接进五件套生成）
- 第三步公共组件：检查是否需要新增，通常直接复用
- 第四步后端：复制 038 的 Service 模式，替换 SQL
- 第五步前端：复制 038 的壳和组件，替换模块内容
- 第六步联调验收

> **时机**：038 M4 跑通后即可启动后续大屏，不需等 038 M5 全部完成。

## 2.5 单模块纵向切片节奏（2026-08-27 增补，task-053/054 验证）

> 对 041 起的大屏模块级开发有效。此前 workflow 只定义了「后端 M1/M2 → 前端 M3/M4」分层批量；041 模块 2 实战验证了更优的**按模块纵向切片**模式，后续模块沿用。

### 切片定义

**一个业务模块 = 一个会话 = 一个编码 task**，task 内一次贯穿该模块的后端端点 + 前端页面 + 切片级联调：

```
契约先行（闸门 A）→ 后端切片 → 前端切片 → 联调对数 → 收尾勾选
```

五件套 tasks.md 的 M1–M5 里程碑条目不重排，作为横向清单由各切片分别认领勾选（如 task-054 完成了「M2 appeal.sql + M4 模块2 + M3 API 封装」三条横切条目）。

### 切片内固定闸门

| 闸门             | 内容                                                                       | 红线                                                 |
| ---------------- | -------------------------------------------------------------------------- | ---------------------------------------------------- |
| **A · 契约先行** | 在 api-contracts.md 起草本模块端点小节 → roadmap §4 立 L3 提案 → 🛑 等会签 | **未会签不写一行实现代码**；等待期只做实库核实等准备 |
| **B · 收尾验收** | acceptance-tests 该模块 P0 场景自动化 + docs 同步自查（无私有引用泄漏）    | 测试不过不进收尾                                     |

首模块切片额外携带 **公共 Service 首建**（双查询抽象 / organId 口径 / 沈抚合并），供其余 5 模块复用——对应第四步 M1。

### 文档 task 与编码 task 分离

L3 文档改动（契约登记 + spec 同步修订）走独立文档审批；审批通过后编码切片才启动。两者可在同一 task 文件中管理，但 §3.1 契约先行必须先于 §3.2+ 完成。

### 切片级联调对数

不等第六步 M5 才对数：每个切片收尾时写 `scripts/query_<NNN>_<module>_integration.py` 直查实库，验证 Service 输出与 DB 直查聚合一致（含沈抚合并、NULL→0、聚合去重边界）。M5 仅剩跨模块项（401/403 全端点、下钻联动、性能）。

### 会签后 review 修正的归宿

用户 review 提出的逐条修正（依赖改造 / 弃用 API 清理 / 抽文件 / PM 配色落定等）**回填已完成 task 的 done/ 文件**（§3 新增「会签后 review 修正」小节 + §5 状态记录），并同步 roadmap 行——**不另立新 task**。遗留视觉回归类事项在 task 头部状态行持续标注。

## 3. 依赖关系图

```
第一步 架构设计
  │
  ├──→ 第二步 PM input + 五件套（每个大屏独立）
  │       │
  │       ├──→ 第四步 后端 M1/M2 ──────────────┐
  │       │                                      │
  └──→ 第三步 公共组件设计+开发 ──────────────┤
                                                 │
              第五步 前端 M3/M4 ←────────────────┘
                 │
                 └──→ 第六步 联调验收 M5
                         │
                         └──→ 第七步 后续大屏复制
```

**并行关系**：

- 第三步（公共组件）∥ 第四步（后端）——互不阻塞
- 第二步（五件套）可在第一步 review 期间提前准备（PM input 迁入不依赖架构定稿）

## 5. 与五件套里程碑的映射

本文的通用步骤与五件套 `plan.md` 的里程碑（M0-M5）映射关系：

| 通用步骤                 | 五件套里程碑 | 说明                                |
| ------------------------ | ------------ | ----------------------------------- |
| 第一步 架构设计          | —            | 不属于单个 spec，是跨 spec 的架构层 |
| 第二步 PM input + 五件套 | M0           | 五件套生成 + design 索引            |
| 第三步 公共组件          | —            | 不属于单个 spec，是跨 spec 的组件层 |
| 第四步 后端              | M1 + M2      | M1 竖切 + M2 批量                   |
| 第五步 前端              | M3 + M4      | M3 壳+首模块 + M4 其余模块          |
| 第六步 联调验收          | M5           | 对数 + 测试 + 性能                  |

> 差异：通用工作流多了第一步（架构）和第三步（公共组件），这两步不属于单个 spec 的 M0-M5，而是跨 spec 的公共前置。
