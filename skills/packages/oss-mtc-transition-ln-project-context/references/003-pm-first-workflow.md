# 003 · PM 优先（PM-first）工作流纪律

> 性质：**长期维护文档**（稳定、与项目无关）
> 日期：2026-09-20
> 适用：AI Agent 在 `oss-mtc-transition-ln` 仓库承接的**任何**工作——bug 修复、数据排查、UI 优化、新功能开发、文档修订
> 与 [002](002-基于skill与docs的协作开发workflow.md) 的关系：002 管「AI + 用户怎么协作」（task 生命周期），本文管「动手前先回答什么问题」——一切任务的前置纪律

---

## 0. 一句话

**任何工作，起点必须是「PM 是怎么定的」，而不是我看到的界面现象、代码现状或直觉。动手前先找到 pm-input / assets / spec 里的权威定义（哪一章哪一行），再谈定性。**

---

## 1. 完整流程（8 步闭环）

```
① 接收信号（用户报告现象 / PM 变更 / 我方发现）
        ↓
② 登记 task（先记录，不定性）—— 现象、期望、涉及模块，标注「🛑 等待拍板」
        ↓
     ※ task 本身仍须过 002 的 review 闸门：③–⑤ 属执行轮排查动作，
       不得在 task 通过 review 前直接开跑（否则违反 002 §10 反模式）
        ↓
③ 回溯源点：PM 是怎么定的？
        - assets txt 原文（一级证据，不可篡改）
        - pm-input 指标算法表 / 功能章节（对 assets 的整理）
        - spec 五件套（pm-input 的推导产物，二级证据）
        ↓
④ 核对我们的实现
        - 后端 SQL / Service 口径
        - 前端组件行为
        - 每层标注：与 PM 一致 / 偏离 / PM 未定义
        ↓
⑤ 判定性（三种结局，都合法）
   a) 实现 ≠ PM → 真 bug，出修复方案
   b) 实现 = PM，现状正确 → ❌ 不成立，记录关闭
   c) PM 自身缺失 / 矛盾 → 升级为开放问题，抛回 PM
        ↓
⑥ 用户 / PM 拍板（AI 永远不替 PM 做需求决定）
        ↓
⑦ 修复 + 验证（tsc / 手测 / 实库对数）
        ↓
⑧ 落 task 状态记录，验收后归档
```

### 快速通道与完整通道

| 通道 | 条件 | 走法 |
| --- | --- | --- |
| 完整通道（默认） | 定性不明 / 涉及数据口径 / 跨模块 | ③–⑥ 一步不少 |
| 快速通道 | 一行级小修且用户口头给出明确方案（如改一个常量值） | 用户拍板结论记入 task 后直接 ⑦，但 ③ 的 pm-input 依据仍须在 task 里引用（引用不到则退回完整通道） |

---

## 2. 为什么「从 PM 开始」是关键

想当然的做法：看到现象 → 对比界面与代码 → 判定 bug → 修。
正确做法多一个前置问题：**「PM 到底要的是什么？」**因为：

1. **现象可能不是问题**——PM 本就无此口径（例：task-082 Bug 3「各渠道信访量」、Bug 4「补助的烈士遗属」，均 ❌ 不成立关闭）；
2. **「不一致」可能不是 bug**——PM 本就把同类指标定义为不同数据源（例：地图取 `letter_screen_4`、柱图取 `letter_screen_5`，PM 未约束两表一致，不能想当然地对数判 bug）；
3. **代码可能才是错的**——看似能跑的实现实际偏离 PM（例：039/040 trend x 轴硬编码「01月~12月」，PM 要求「最近 12 个月动态标签」）。

---

## 3. 定性结论的三种出口

| 结局 | 判据 | 后续动作 |
| --- | --- | --- |
| a) 真 bug | 实现 ≠ PM 明文要求 | 修复方案写入 task §「修复方案」，🛑 等 review，通过后实施 |
| b) ❌ 不成立 | 现状与 PM 一致 / PM 无此口径 | task 记录排查链 + 证据（逐层核对结果），关闭归档 |
| c) PM 定义缺失 / 矛盾 | pm-input / assets 未定义或自相矛盾 | 抛回 PM：bug 类记 task「🛑 等待用户/PM」；涉及 spec 的走 spec §9 开放问题（正式渠道），勿自行补需求 |

---

## 4. 硬规则（AI Agent 必须遵守）

1. **先引后做**：task / 分析输出中，PM 依据必须落到「文件 + 章节/行号」，引用前须实际 Read 验证存在（AGENTS.md §8 反幻觉规则在流程层的延伸）。
2. **不替 PM 定需求**：出现「PM 没写但我觉得应该…」的空缺时，一律停在 ⑤c 抛回，不自行填补。
3. **不对数先于定性**：两处数据不一致时，禁止先入为主「必然是实现 bug」；先查 PM 是否定义了同源同口径。
4. **拍板留痕**：任何快速通道、用户口头结论，都须回填 task 状态记录后再动代码。
5. **修改 docs/ 的口径结论**：属 L3，走 roadmap §6 提案审批（见 AGENTS.md §10），本纪律不豁免任何文档门禁。
