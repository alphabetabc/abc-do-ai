## 1. 总览：5 阶段流程

```
[阶段 0] 想法输入
   ↓ 用户
[阶段 1] 文档阅读
   ↓ AI：加载 skill + 扫相关 docs
[阶段 2] 建立 task（plans/）
   ↓ AI：判定任务类型 + 选模板 + 写 task 文件
   ↓ 🛑 用户 review task → 通过
[阶段 3] 执行 task
   ↓ AI 按 task 步骤执行；遇 🛑 停下来等用户
   ↓ task 完成
[阶段 4] 验收 + 归档
   ↓ 🛑 用户验收
   ↓ 归档到 plans/done/
   ↓ 跑防漂移 review checklist
```

**核心原则**：task 文件 = 用户 review 单元 = AI 执行脚本。每个 task **必须经过用户 review 才能执行**；task 完成 **必须等用户验收才能归档**。

## 2. 角色分工

### 2.1 用户（PM / 架构师 / 研发负责人）

| 职责   | 动作                                                                 |
| ------ | -------------------------------------------------------------------- |
| 输入   | 想法 / 需求 / 决策 / 反馈（文字、PM 输入、修订指令）                 |
| review | review AI 生成的 task 文件；review 五件套草稿；review 关键 spec 决策 |
| 拍板   | 业务规则、验收口径、技术选型、开放问题关闭                           |
| 验收   | task 完成后的产出物                                                  |

### 2.2 AI Agent

| 职责      | 动作                                                    |
| --------- | ------------------------------------------------------- |
| 文档阅读  | 加载 skill + 扫相关 docs；建立项目私域上下文            |
| task 建立 | 按 §3 判定任务类型 → 选模板 → 写 task → 停下等 review   |
| task 执行 | 按 task 文件 §1 步骤逐项执行；遇 `🛑 等待用户` 必须停下 |
| 自检      | 每步完成后跑 §7 自检清单                                |
| 防漂移    | 任务归档前跑 §8 review checklist                        |

### 2.3 边界

| 场景                 | 谁做                                                                           |
| -------------------- | ------------------------------------------------------------------------------ |
| 业务规则拍板         | 用户                                                                           |
| 表字段命名、API 形状 | 必须以 `docs/design/data-models.md` / `api-contracts.md` 为准；AI 不得擅自新增 |
| 五件套开放问题关闭   | 用户拍板；AI 仅整理候选                                                        |
| docs L3 改动提案     | AI 起草 → 用户 review → 走 `plans/roadmap-*.md` §6 提案审批                    |
| skill 文件改动       | L1 自由（AI 可直接编辑）                                                       |
| 反幻觉自检           | AI 必做（不得编造路径/章节/字段/数据）                                         |

## 3. task 三分类（任务类型判定）

**第一问：这次任务要改什么？**

| 类型              | 判定标准                                          | task 模板                                      | 示例                                                           |
| ----------------- | ------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| **仅 docs 维护**  | 不涉及代码改动；只改 `docs/**/*.md`               | 通用模板（轻量）                               | 补 design/data-models.md §6 字段注释；修 specs/index.md 状态列 |
| **仅 skill 维护** | 不涉及代码改动；只改 `.trae/skills/.../...md`     | 通用模板（轻量）                               | 改 references/001 章节结构；归档 task                          |
| **编码**          | 涉及 backend/ frontend/ migration/ SQL 等代码改动 | 通用模板（轻量） 或 SDD 五件套模板（复杂特性） | 修一个 SQL bug；实现 specs/NNN-\*/plan.md M1                   |

**第二问：是否涉及新特性（多阶段、需五件套）？**

- **是**（新特性 / 大改动）→ 用 [`task-template-sdd-全流程.md`](../plans/templates/task-template-sdd-全流程.md)（三阶段 + 内嵌 prompt 章节）
- **否**（单一改动 / 单一 bug）→ 用 [`task-template-通用.md`](../plans/templates/task-template-通用.md)（轻量：元信息 + 步骤 + 依据 + 状态）

### 3.1 SDD 五件套模板 vs 通用模板

| 维度             | SDD 五件套模板                     | 通用模板                      |
| ---------------- | ---------------------------------- | ----------------------------- |
| 适用             | 新特性（pm-input → 五件套 → 编码） | 单一改动、bug 修复、文档修订  |
| 内嵌 prompt 章节 | ✅ 有（§4 复制即用）               | ❌ 无（task 本身就是 prompt） |
| 闸门             | §1.3 / §2.3 / §3.3 多闸门          | §1 步骤里标 `🛑 等待用户`     |
| 用户 review 重点 | 三阶段分轮产物                     | 步骤清单 + 验收标准           |

## 4. task 文件结构（基于通用模板）

完整模板见 [`plans/templates/task-template-通用.md`](../plans/templates/task-template-通用.md)。

### 4.1 必填字段

- **类型**：`仅 docs 维护` / `仅 skill 维护` / `编码`（必填，三选一）
- **影响范围**：要修改或创建的文件路径清单
- **验收标准**：用户用来判断"是否完成"的清单（用户填写或与 AI 协商）
- **步骤**：AI 执行的步骤清单；需要用户介入的步骤标 `🛑 等待用户：{等什么}`
- **依据**：任务来源（skill 路径 / docs 路径 + 引用章节）

### 4.2 文件命名

```
plans/task-{日期}-{编号}-{slug}.md
```

- 日期：`YYYY-MM-DD`
- 编号：当日序号，如 `001` / `002`
- slug：英文短描述，如 `038-后端api-初稿`

示例：`plans/task-2026-08-12-001-038-后端api初稿.md`

### 4.3 文件存放位置

- 进行中：`plans/`（详见 [AGENTS.md §10.1](../../AGENTS.md)）
- 已完成：移动到 `plans/done/`（保留原文件名）

## 5. task 生命周期

```
[⚪ 待启动] plans/task-xxx.md
   ↓ AI 写完 task → 🛑 用户 review
[🟡 进行中]
   ↓ AI 按 §1 步骤执行
[🟡 待验收]
   ↓ AI 完成 → 🛑 用户验收
[✅ 已完成]
   ↓ 移动到 plans/done/
   ↓ 跑防漂移 review checklist
[✅ 已归档]
```

详见 [AGENTS.md §10.1](../../AGENTS.md)。

## 6. 多轮协作节奏

### 6.1 task 建立轮

**AI 动作**：

1. 判定任务类型（§3）
2. 选模板并复制到 `plans/task-{日期}-{编号}-{slug}.md`
3. 填充 §0 元信息 + §1 步骤（步骤尽量细，每步能独立 review）+ §2 依据
4. 写入 `🛑 等待用户：review task` 标记
5. **停下**，告诉用户"task 已写好，请 review"

**用户动作**：

- review task 文件：步骤是否清晰？验收标准是否合理？依据是否准确？
- 通过 → AI 进入执行轮
- 不通过 → 修改 task（用户改 / 用户反馈 AI 改）

### 6.2 task 执行轮

**AI 动作**：

1. 按 §1 步骤顺序执行
2. 每步完成后跑 §7 自检清单
3. 遇 `🛑 等待用户` 必须**立即停下**，等用户反馈
4. 所有步骤完成 → 进入验收轮

### 6.3 task 验收轮

**AI 动作**：

1. 跑 §8 防漂移 review checklist
2. **停下**，告诉用户"task 已完成，请验收；产出物清单如下"
3. 用户验收通过 → 移动 task 到 `plans/done/`，更新 [roadmap](../plans/roadmap-2026-08-11-big-screen.md) §4（如适用）

**用户动作**：

- 验收：检查产出物 vs §0 验收标准
- 通过 → 通知 AI 归档
- 不通过 → 反馈修订点；AI 进入新一轮修订

## 7. AI 自检清单（每步完成后必跑）

### 7.1 反幻觉自检（强制）

> 完整规则：[AGENTS.md §8](../../AGENTS.md)

- [ ] 引用的所有文件路径已实际 `Read` / `Grep` / `Glob` 验证存在
- [ ] 引用的章节编号与当前文件一致（未编造）
- [ ] 表字段名、枚举值、SQL 结果**未凭推测填充**（未知标"待验证"）
- [ ] 未声称"已完成"未实际执行的操作
- [ ] docs/ 文档未引用 `.trae/` / `AGENTS.md` / `.local-*`

### 7.2 任务类型自检

| 类型          | 自检项                                                                     |
| ------------- | -------------------------------------------------------------------------- |
| 仅 docs 维护  | 改动文件全部在 `docs/` 下；L3 改动走完 roadmap 提案审批                    |
| 仅 skill 维护 | 改动文件全部在 `.trae/skills/` 下；不影响他人会话                          |
| 编码          | SQL 入 `repositories/sql/` 不入 migration；端点先更 api-contracts 再写代码 |

### 7.3 引用一致性自检

- [ ] 改动 docs 后，[references/001 §7.4](001-docs名词解释与维护使用指南.md) 反幻觉清单通过
- [ ] 改动 skill 后，本文档（002）仍准确（必要时更新本文件）
- [ ] 改动 design/ 后，引用该文档的 spec/ 文档已知（不需要立即改但记入提醒）

## 8. 防漂移 review checklist

**触发时机**：每个 task 归档**前** + 用户**手动**触发 + 阶段性（如每特性完成时）。

### 8.1 skill 内防漂移

- [ ] `references/001` 的目录结构表（§2）仍准确反映 `docs/` 现状
- [ ] `references/001` 的名词速查表（§3）仍覆盖新增术语
- [ ] `references/001` 的硬规则清单（§10）仍与 [design/001](../design/001-big-screen-dev-guide.md) §3 一致
- [ ] 本文档（002）的流程描述仍匹配实际操作
- [ ] `design/001` §1 docs 现状盘点仍准确（定期刷新）
- [ ] `design/001` §5 docs 内部矛盾跟踪已更新
- [ ] `roadmap` §4 任务索引状态列已同步

### 8.2 docs/ 内防漂移

- [ ] `docs/index.md` 分区说明仍准确
- [ ] `docs/specs/index.md` 编号 / 状态表已更新
- [ ] `docs/design/system-overview.md` §2.2.2 菜单/路由表已同步
- [ ] `docs/design/data-models.md` §6/§7 表结构与代码一致
- [ ] `docs/design/api-contracts.md` §7 端点与代码一致
- [ ] `docs/skills/` 各栈 coding.md 与现版本号一致
- [ ] `docs/standards/coding-standards.md` §1 SSOT 规则无违反

### 8.3 反向引用防漂移

- [ ] docs/ 内文档未引用 `.trae/` / `AGENTS.md` / `.local-*`（违反 [docs-no-private-refs](../../.trae/rules/docs-no-private-refs.md) 规则）
- [ ] skill 内文档未引用 docs/ 内已废弃内容
- [ ] AGENTS.md §2.1 模块表与大屏实际模块一致

### 8.4 漂移处理

| 漂移类型               | 处理                                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| 内容过时（信息陈旧）   | 建立新 task 修订                                                              |
| 引用断裂（路径不存在） | 修复引用 / 重建目标                                                           |
| 矛盾（多文档不一致）   | 走 roadmap §6 提案审批                                                        |
| 漂移不可恢复           | 记入 [design/001 §5](../design/001-big-screen-dev-guide.md) docs 内部矛盾跟踪 |

## 10. 常见反模式

| 反模式                                      | 为什么错                  | 正确做法                                     |
| ------------------------------------------- | ------------------------- | -------------------------------------------- |
| AI 写完 task 直接执行不 review              | 用户失去 review 节点      | task 完成 → 🛑 用户 review → 通过才执行      |
| AI 跳过 task 直接改 docs                    | task 失去 review 单元价值 | 所有 docs/ skill/ 改动必须先建 task          |
| task 不写验收标准                           | 验收无依据                | §0 验收标准必填                              |
| task 步骤过于笼统                           | 用户无法 review 具体性    | 步骤细化到"做什么 / 输出什么 / 是否等待"     |
| AI 完成后不通知用户验收                     | 用户不知道何时验收        | 完成时立即停下，通知用户 + 列产出物清单      |
| 任务归档前不跑防漂移                        | 漂移积累                  | 归档前必跑 §8 checklist                      |
| task 文件写到一半就执行                     | 中断后上下文丢失          | task 完整后才进入执行轮                      |
| 在 task 里加内嵌 prompt 章节（除 SDD 模板） | 通用 task 应简洁          | 通用模板无 prompt 章节；task 本身就是 prompt |
| 反幻觉自检省略                              | 编造风险                  | §7.1 必跑                                    |
