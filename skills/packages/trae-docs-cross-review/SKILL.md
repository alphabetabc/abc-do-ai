# trae-docs-cross-review（通用交叉 Review 基座）

对任务计划 / 调研 / 设计 / 元方案文档做深度交叉 review，目标是让文档**真的能支撑开发**（事实可验证 + 逻辑闭环 + 盲区排查，三者缺一不可）。

> **本 skill 是跨项目通用的方法论基座**，不绑定任何特定项目。推荐做法是让项目方提供一份独立的 review config，由本 skill 在执行前加载；为了兼容存量项目，也允许从现有 `<project>-docs-cross-review` skill 的 `## Project-Specific Config` 章节读取项目特化配置。本 skill 自身只承担方法论与配置协议。

---

## 1. When to Invoke

- 用户说"review 这个计划/文档/方案"
- 用户说"交叉 review"、"深度 review"、"帮我看看这个文档能不能支撑开发"
- 用户准备执行某份变更计划前想做最后把关
- 用户对某份调研/设计文档的质量没把握

**不要用于**：

- 纯代码 diff review（那是代码审查 skill 的职责）
- 快速过一遍（本 skill 是深度 review，单次耗时较长；快速过一遍走 §6 降级规则：单视角快速通道）
- 非文档对象（如纯配置文件 / 数据库 schema）：本 skill 只 review 文档

## 2. Conventions（约定）

### 2.1 常见审查对象路径

如果用户没有显式指定 review 对象，可以优先从这些常见路径中寻找；如果文档位于其他位置，直接以用户指定路径为准：

| 类型          | 默认路径                           | 说明                   |
| ------------- | ---------------------------------- | ---------------------- |
| 变更计划      | `.trae/documents/plans/task-*.md`  | 执行前最后把关         |
| 调研文档      | `.trae/documents/research/**/*.md` | 事实性是否扎实         |
| 设计/架构文档 | `.trae/documents/design/**/*.md`   | 含各子目录             |
| 元方案        | 跨阶段的总计划                     | 由调用方指定           |
| 不审查        | `AGENTS.md` / `.trae/rules/`       | 规则源，不是被审查对象 |
| 不审查        | `*.bak` / `backup/`                | 历史快照，非活代码     |

### 2.2 报告存放路径

默认存到 `.local-review/` 目录下，文件名格式为 `report-{NNN}.md`（三位序号，从 `001` 开始递增，例如 `report-001.md`、`report-002.md`）。

**序号取数规则**（避免并发冲突）：

1. 扫描 `.local-review/` 下所有形如 `report-*.md` 的文件名
2. 提取文件名中的数字部分（如 `report-007.md` → `7`）
3. 取最大值 + 1 作为本次序号；如果目录下没有任何 `report-*.md`，则从 `001` 开始
4. **写入策略**（降低并发冲突概率）：
   - 先以临时名 `report-{NNN}.tmp.md` 写入内容
   - 写入完成后再 rename 为 `report-{NNN}.md`
   - 极端并发场景下仍可能产生相同 N，由用户处理覆盖 / 合并

**执行时自动初始化**（由本 skill 负责，不依赖项目预配置）：

1. 检测 `.local-review/` 目录是否存在；不存在则创建
2. 在该目录下创建 `.gitignore`，内容为忽略全部：
   ```
   *
   !.gitignore
   ```
3. 如果用户显式指定了其他路径，则跳过上述自动初始化，以用户指定为准

### 2.3 输出语言

与被 review 文档语言一致；如未指定则默认中文。

### 2.4 Review Modes（执行模式）

本 skill 支持 3 种模式：

| 模式          | 适用场景                                             | 核心证据来源                         | 重点                                 |
| ------------- | ---------------------------------------------------- | ------------------------------------ | ------------------------------------ |
| `repo-backed` | 文档对应已有仓库代码 / 调用方 / 运行对象             | 仓库代码、检索结果、运行验证         | 事实核查、调用方完整性、实现一致性   |
| `doc-only`    | 绿地方案、纯设计稿、外部 RFC / PRD、尚未落代码的方案 | 文档正文、引用资料、用户给出的上下文 | 逻辑闭环、假设显式化、风险与验证设计 |
| `mixed`       | 有部分代码、部分历史实现或只覆盖局部模块             | 代码 + 文档混合                      | 证据分层、边界澄清、缺口识别         |

如果用户未指定模式，默认按可获得证据自动判断：

- 找得到对应仓库实现或调用方，优先用 `repo-backed`
- 只有文档与设计材料，用 `doc-only`
- 两者都有但覆盖不全，用 `mixed`

### 2.4.1 `repo-backed`（默认）

适用场景：文档对应已有仓库实现 / 调用方 / 可运行对象。

**证据来源**（按优先级）：

1. 仓库代码（最高级）
2. 运行验证（build / type check / 单元测试）
3. `.trae/documents/` 文档
4. 模型记忆（最低级，禁止作为唯一结论来源）

**执行要点**：

- 视角 A / C 必须用仓库检索能力（grep / rg / 代码搜索）当场验证
- 视角 B 的"步骤可执行性"必须检查到文件级
- "未验证假设"几乎不应该出现；出现就要标记降级

### 2.4.2 `doc-only`

适用场景：绿地方案 / 纯 RFC / 外部 PRD / 还没有落地代码的前置设计。

**证据来源**（按优先级）：

1. 当前文档正文 + 明确引用的外部资料
2. 项目内上下文文档
3. 模型记忆（最低级，仅作为辅助）

**执行要点**：

- **必须**把文档中的"假设 / 通常 / 预期 / 依赖外部"等模糊描述转为显式假设表（见 §7.2 第 9 条）
- **必须**为每个核心决策列出"如何验证"，而不是只给结论
- 视角 A 的事实核查变为"逻辑事实核查"：内部一致、引用真实、术语一致
- 视角 C 的盲区排查重点：未覆盖的场景、未列出的边界、未引用的相关方
- "未验证假设"会被大量使用，这是 `doc-only` 的常态，不是缺陷；报告中要明确标出"由于 `doc-only` 模式限制，本条目无法用代码验证"

### 2.4.3 `mixed`

适用场景：部分有代码、部分只有文档 / 历史资料；或代码只覆盖局部模块。

**证据来源**：按主题分层

- 能落到代码的结论 → 按 `repo-backed` 处理
- 落不到代码的结论 → 按 `doc-only` 处理

**执行要点**：

- 主对话在启动三视角前，先按主题拆分证据等级（哪些条目有代码证据、哪些只有文档证据）
- 把拆分结果作为指令的一部分传给 subagent
- 报告里每条结论必须标注证据等级：`[代码证据]` / `[文档证据]` / `[未验证假设]`

### 2.5 Project Config（项目配置加载）

推荐把项目差异收敛成一份独立配置，而不是复制整份通用方法论。执行时按下面顺序确定项目特化信息：

1. **用户显式指定的 config 路径**：优先级最高（如 `--config ./configs/project-review-config.yaml`）
2. **项目根目录的约定配置文件**：项目方在自己的项目根目录下维护 config，推荐 `./configs/project-review-config.yaml`；也允许团队约定其他路径。**注意**：本 skill 包内部的 `configs/project-review-config.template.yaml` 被 `beehive-skill.json` 的 `files` 字段锁定，**项目方不能修改这个文件**（修改会被判定为改 skill），只能在自己的项目目录维护独立 config
3. **兼容回退**：如果没有独立 config，但存在 `<project>-docs-cross-review/SKILL.md`，则读取其中的 `## Project-Specific Config` 章节
4. **仍未找到**：按纯通用模式执行，不注入项目特化规则

项目 config 只负责承载差异信息，例如：

- 文档默认路径
- 不审查清单
- 项目契约
- 盲区关键词
- 性能红线
- 历史禁区 API
- 报告默认输出位置

**首次使用必做**：项目方第一次接入本 skill 时，应参考 `configs/project-review-config.template.yaml` 的 schema，在自己的项目目录创建独立 config（如 `./configs/project-review-config.yaml`），**删除模板里的示例内容**，按需填入真实项目特化信息。模板里的示例值仅作语法演示，不是默认值。

## 3. 核心原则（自包含，不外引）

本 skill 遵循以下原则，无需引用外部文档：

1. **证据优先**：所有结论都必须基于当前可获得的证据（仓库检索 / 文件读取 / 用户提供文档 / 必要时运行验证），不能基于记忆/推测
2. **证据优先级随模式变化**：
   - `repo-backed`：仓库代码 > 运行验证（build/测试） > 文档 > 模型记忆
   - `doc-only`：当前文档正文 / 明确引用资料 > 相关上下文文档 > 模型记忆
   - `mixed`：对能落到代码的结论按 `repo-backed`；落不到代码的结论按 `doc-only`
3. **禁止推测当结论**：无法用当前模式下的可得证据支撑的内容，只能标注"未验证假设"或"文档缺少证据"，不能作为事实结论输出
4. **review 与修改分离**：本 skill 只产出报告，不自动改被 review 的文档

## 4. Core Mechanism：三视角独立 Review + 对抗式交叉验证

Trae 主对话只有一个模型，但可以借助**当前环境支持的并行子任务 / subagent 能力**，让多个视角分别完成 review，再做一轮**对抗式交叉验证**。如果当前环境不支持并行 subagent，则退化为主对话按 A → B → C 顺序串行完成，最后再自行做一次交叉验证。

### 4.1 为什么是三视角 + 对抗式

- **单视角 review 的盲区**：架构师关注设计合理性，但可能漏掉调用方影响；测试工程师关注验证覆盖，但可能不深究性能；文档审查员关注完整性，但可能不验证事实
- **对抗式的价值**：第一轮 review 的结论可能是错的（subagent 也可能幻觉），需要第二轮交叉验证来确认
- **事实优先**：所有结论必须本地可验证，不能基于记忆/推测

### 4.2 三视角定义

| 视角                    | 推荐执行方式                                      | 关注点                                                                                           | 产出                    |
| ----------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------- |
| **A. 事实核查员**       | 优先用检索能力较强的 subagent；没有就由主对话执行 | 文档里的事实结论能否用当前模式下的证据当场验证？路径/API/数字/引用是否准确？是否有幻觉？         | 事实错误清单（带证据）  |
| **B. 架构与逻辑审查员** | 优先用通用推理型 subagent；没有就由主对话执行     | 背景→现状→目标→步骤→验证→风险→回退 的逻辑链是否闭环？决策是否自洽？方案是否可行？                | 逻辑断点清单 + 决策质疑 |
| **C. 盲区排查员**       | 优先用检索能力较强的 subagent；没有就由主对话执行 | 主动找未覆盖的文件/调用方/边界场景。关键影响面是否都被摸清？有没有漏掉的依赖、场景、假设或死角？ | 盲区清单（带证据）      |

### 4.3 对抗式交叉验证（第二轮）

三个 subagent 的产出汇总后，主对话做一轮交叉验证：

1. **A 的事实结论 vs B 的逻辑断点**：B 质疑的某点，A 是否有事实证据支持/反驳？
2. **C 的盲区 vs B 的方案**：C 发现的盲区，B 的方案是否已覆盖？
3. **A 的行号验证 vs C 的 grep 结果**：A 说"L123 是 X"，C grep 出来的实际调用方是否和 A 说的一致？
4. **降级规则**：任何视角的结论如果无法用当前模式下的证据验证，标注为"未验证假设"而非结论

### 4.4 执行能力映射（避免绑死工具名）

本 skill 依赖的是**能力**，不是某一套固定工具名。执行时请按当前环境做映射：

- **并行子任务能力**：能并行起多个 subagent 就并行；否则串行执行三视角
- **仓库检索能力**：可用 `rg`、代码搜索、grep 类能力定位调用方 / 路径 / API
- **文件读取能力**：可用编辑器读取、`Get-Content`、Read 类能力查看具体实现
- **文档证据能力**：可读取当前方案文档、引用文档、用户提供资料
- **结果汇总能力**：主对话统一做严重度分级与对抗式交叉验证

如果当前环境提供专门的代码库子代理，优先让视角 A / C 使用；视角 B 可以由主对话或通用推理型子代理执行。

## 5. How to Use

### 5.1 步骤 1：明确 review 范围

向用户确认：

1. 要 review 哪份文档（或哪几份）？
2. review 报告存到哪个路径？（用户可显式指定；默认 `.local-review/report-{NNN}.md`，由 skill 自动创建目录和 `.gitignore`）
3. 当前更适合哪种模式？（`repo-backed` / `doc-only` / `mixed`；如果用户没说，就由主对话根据证据自动判断）
4. 是否有特别关注的点？（如"重点看性能预算是否合理"）
5. **是否有项目 config 可加载**？如有，优先使用显式 config 路径；没有时再回退到现有 `<project>-docs-cross-review` skill

### 5.2 步骤 2：并行启动三个视角进行 review

在启动三视角前，先完成**项目配置加载**。优先使用显式 config；如果没有，再尝试约定路径；仍没有时，最后兼容读取现有 `<project>-docs-cross-review` skill 的 `## Project-Specific Config`。

完成配置加载后，优先使用**当前环境支持的并行 subagent 能力**一次性拉起 3 个视角（最大化并行）；如果环境不支持并行 subagent，就由主对话按 A → B → C 顺序执行。

```
视角 A（事实核查员）:
  - 读被 review 的文档
  - 提取每个事实结论（行号/路径/API/数字）
  - 用当前模式允许的证据来源当场验证
  - 产出：事实错误清单（带证据）

视角 B（架构逻辑审查员）:
  - 读被 review 的文档
  - 检查逻辑链闭环、决策自洽、方案可行性
  - 产出：逻辑断点清单 + 决策质疑

视角 C（盲区排查员）:
  - 读被 review 的文档
  - `repo-backed` / `mixed`：检索提到的 API/函数/字段/调用方
  - `doc-only`：检索文档中的依赖关系、引用、前置假设、未覆盖场景
  - 产出：盲区清单（带证据）
```

**关键**：每个子任务的指令必须包含：

- 被 review 文档的绝对路径
- 本次使用的 review mode（`repo-backed` / `doc-only` / `mixed`）
- 该视角的具体检查清单（见 §7）
- 本次加载到的项目 config 内容；如果没有独立 config，则附上兼容回退得到的 `## Project-Specific Config` 内容
- 要求产出格式（带证据，禁止推测当结论）
- 明确"不要修改任何文件，只做 review 产出"

### 5.3 步骤 3：主对话汇总 + 对抗式交叉验证

三个 subagent 返回后，主对话：

1. 汇总三份产出
2. 做对抗式交叉验证（见 §4.3）
3. 按严重程度分级：**高（必须修）/ 中（建议优化）/ 低（可选改进）**
4. 每条带：具体问题 + 证据 + 修复建议

### 5.4 步骤 4：写 review 报告到用户指定路径

报告格式见 §8。

### 5.5 步骤 5：等用户确认是否修改

报告产出后**暂停**，等用户 review 报告并决定：

- 哪些条目要修
- 修改由谁做（用户自己改 / 主对话改 / 再起 subagent 改）

**不要自动修改被 review 的文档**——review 和修改必须分离，避免"自己改自己 review"。

## 6. 降级规则：单视角快速通道

三视角并行是默认模式，但以下场景**降级为单视角**，避免过度审查：

| 场景                        | 降级到                         | 理由                                     |
| --------------------------- | ------------------------------ | ---------------------------------------- |
| 文档 < 100 行的小 task      | 仅视角 A（事实核查）           | 小文档逻辑链短，主要风险是事实错误       |
| 纯调研文档（无步骤/无回退） | 视角 A + 视角 B（跳过 C 盲区） | 调研文档不涉及调用方影响，盲区排查收益低 |
| 用户明确说"快速过一遍"      | 仅视角 A                       | 用户已接受低严谨度                       |
| 紧急阻塞、用户要立刻决策    | 仅视角 B（架构逻辑）           | 时间紧时优先保逻辑闭环                   |

**降级时必须**在报告"总评"里标注"本次 review 降级为单视角 X，未做完整三视角交叉验证，结论严谨度相应降级"。

## 7. 各视角检查清单（通用版）

### 7.1 视角 A：事实核查员

对文档里每个**事实性陈述**，用当前模式允许的证据当场验证：

1. **行号/引用验证**：文档引用某个实现、章节、接口或文件段落时，确认引用目标是否真的存在且内容一致
2. **路径验证**：文档引用的文件路径是否存在？
3. **API / 契约验证**：文档描述某个接口、hook、状态结构或协议时，确认其签名和语义是否一致
4. **数字验证**：文档里的性能数值、数量级、容量上限、超时时间等有没有来源？是文档记录、实测还是假设？
5. **调用方清单验证**：若文档声称"X 有 N 个调用方"，实际命中几个文件？若是 `doc-only`，则检查依赖方/责任方是否列全
6. **死代码验证**：文档说"X 是死代码无调用方"——grep X，确认是否真的 0 调用方
7. **状态/字段验证**：文档说"Y 是死字段"或"某状态未被使用"——确认是否真的无读写/无消费方

**禁止**：把文档自己的陈述直接当成事实来源。`repo-backed` / `mixed` 优先落到代码或运行证据；`doc-only` 至少要落到文档内引用、前后文或用户给出的材料。

### 7.2 视角 B：架构与逻辑审查员

检查文档的**逻辑链和决策自洽性**：

1. **背景→现状→目标 链条**：背景说的问题，现状是否真的存在？目标是否真的解决问题？
2. **决策矩阵自洽**：每个决策的"倾向 A/B"是否和理由一致？有没有"倾向 A 但理由支持 B"的矛盾？
3. **步骤可执行性**：步骤是否能独立 commit + 回退？步骤间依赖是否标注？有没有"步骤 X 依赖步骤 Y 但 Y 在 X 后面"的顺序错误？
4. **风险覆盖**：识别的风险是否都有缓解措施？有没有"识别了风险但没给缓解"的悬空风险？
5. **验证完整性**：验证方案是否覆盖所有改动点？有没有"改了 X 但验证清单里没 X"的遗漏？
6. **回退方案**：每个步骤的回退路径是否真的能回退？有没有"步骤 X 和 Y 改了同一文件，回退 X 会破坏 Y"的冲突？
7. **契约一致性**：[由项目特化版 `## Project-Specific Config` 章节注入具体契约清单] —— 若项目特化版提供了"禁用 API 清单 / 状态写路径契约"，则按其检查；否则只做通用语义层面的"逻辑一致"检查
8. **反例与边界测试**：针对文档中的 API/函数/流程，强制找至少 **3 个恶意/异常输入场景**（空值、超大并发、权限越权、状态悬挂）。检查文档是否明确了这些场景下的系统行为（报错？降级？重试？）。未覆盖 → 标记**【高影响漏洞】**
9. **假设显式化**：扫描文档中的模糊描述（"通常"、"一般"、"预期"、"依赖外部"），转为显式假设表：

   | ID  | 假设内容                   | 风险等级 | 是否已验证   |
   | --- | -------------------------- | -------- | ------------ |
   | A1  | 假设 X 在 Y 场景下不会发生 | 高       | ❌（无证据） |

   若存在仓库代码或依赖清单，再交叉比对假设中提到的版本号、组件或前置条件是否与现状冲突。

10. **可测试性审查**：仅凭这份文档，测试工程师能否写出完整测试用例？输出明确的**测试覆盖缺口清单**

### 7.3 视角 C：盲区排查员

主动找文档**没覆盖的东西**：

1. **影响面完整性**：文档说"X 有 N 个调用方 / 依赖方 / 使用方"，实际是否列全？
2. **相关对象未被提及**：文档讨论 A 时，还有没有强关联模块 / 角色 / 依赖 / 接口完全没提？
3. **死代码/死字段遗漏**：文档说"某机制是死代码"——还有没有其他类似的死代码、死配置、死假设没被提到？
4. **边界场景遗漏**：文档讨论了 A/B/C 场景，还有没有其他交互场景、失败场景、并发场景、迁移场景没被讨论？
5. **文档间引用一致性**：文档 A 引用文档 B 的 §X.Y，B 里是否真的有这个章节？内容是否一致？
6. **备份文件/历史遗留**：grep `.bak` / `backup/`，有没有备份文件没被清理？
7. **跨目录影响**：改 a/ 的东西，是否影响 b/ 或 c/ ？
8. **项目特化盲区**：[由项目特化版 `## Project-Specific Config` 章节注入项目特定盲区检查点] —— 例如性能红线、特定状态契约、历史禁区 API 等

## 8. Report Format

报告必须按统一格式产出。**完整模板字符串见 [`./templates/report-format.md`](./templates/report-format.md)**；本节只列章节清单与填充规范。

**必须包含的章节**：

| 章节              | 内容要点                                                         | 必填 |
| ----------------- | ---------------------------------------------------------------- | ---- |
| 顶部元数据        | Reviewer / 日期 / 文档路径 / Review Mode / 项目特化版 / 事实依据 | ✅   |
| §0 总评           | 评级（A / B+ / B / C）+ 一句话总评 + 整体判断（2-3 句）          | ✅   |
| §1 必须修复（高） | 每个问题带 事实 / 风险 / 修复建议 / 验证视角                     | ✅   |
| §2 建议优化（中） | 同 §1 格式                                                       | ✅   |
| §3 可选改进（低） | 同 §1 格式                                                       | ✅   |
| §4 关键事实补充   | subagent 独立验证的事实，与文档陈述对照                          | ✅   |
| §5 总结           | 必须修 / 建议 / 可选 三档摘要 + 进入下一阶段判断                 | ✅   |

**填充规范**：

- 严重度标签：`[高]` / `[中]` / `[低]`，分别对应 §1 / §2 / §3
- 占位符 `{xxx}` 在产出时替换为真实数据，不要把花括号留在报告里
- **降级标注**：如果本次 review 降级为单视角（见 §6），必须在 §0 总评里加一行"本次 review 降级为单视角 X，未做完整三视角交叉验证"
- **未验证假设标注**：`doc-only` / `mixed` 模式下产生的"无法用代码验证"的结论，必须在条目里显式标注【未验证假设】

## 9. Project Config Protocol

本 skill 推荐采用**配置驱动**方式承载项目差异，而不是为每个项目复制一整份通用方法论。建议项目侧提供一份独立 config，字段至少覆盖以下信息：

| 字段                  | 用途             | 说明                                   |
| --------------------- | ---------------- | -------------------------------------- |
| `project_name`        | 标识项目         | 纯展示字段，便于报告输出               |
| `default_doc_paths`   | 默认文档查找路径 | 覆盖 §2.1 的常见路径                   |
| `exclude_paths`       | 不审查清单       | 如 `AGENTS.md`、备份目录               |
| `contracts`           | 项目契约         | 注入 §7.2 第 7 条                      |
| `blindspot_checks`    | 项目盲区检查点   | 注入 §7.3 第 8 条                      |
| `forbidden_apis`      | 历史禁区 API     | 可并入契约检查                         |
| `performance_rules`   | 性能红线         | 项目特有的预算或边界                   |
| `report_default_path` | 报告默认输出位置 | 可覆盖 `.local-review/report-{NNN}.md` |
| `notes`               | 其他说明         | 可选，用于补充上下文                   |

推荐把配置文件放在当前 skill 的 `configs/` 目录下，例如 `configs/project-review-config.yaml`；也允许团队自行约定其他路径。可参考同目录下 `configs/project-review-config.template.yaml` 模板编写。

### 9.1 推荐流程

1. 先读取通用版 `trae-docs-cross-review/SKILL.md`
2. 再加载项目 config
3. 把 config 中的项目差异注入到 §2、§7、§8 的对应位置
4. 按同一套三视角逻辑执行 review

### 9.2 兼容存量项目

如果某个项目还没有独立 config，但已经存在 `<project>-docs-cross-review/SKILL.md`，则可以把该文件末尾的 `## Project-Specific Config` 章节视作**兼容层配置源**：

1. 优先读取独立 config
2. 没有独立 config 时，再读取 `## Project-Specific Config`
3. 两者都没有时，回退到纯通用模式

这样可以先演进通用版，不必立即改动存量项目版 skill。

### 9.3 项目配置作者指南

项目 config 应尽量只写**差异信息**，不要重复三视角方法论、报告格式、降级规则等通用逻辑。换句话说：

- **通用版负责怎么 review**
- **项目 config 负责 review 什么、避开什么、重点盯什么**

**配置路径约定**（必读）：

- 项目 config 应放在**项目自己的目录**（推荐 `./configs/project-review-config.yaml`），不是 skill 包内的 `configs/`
- skill 包内 `configs/project-review-config.template.yaml` 是模板，被 `beehive-skill.json` 锁定，**项目方不能修改**
- 首次接入时应在自己项目目录下创建独立 config，删除模板里的所有示例内容，按需填写真实项目特化信息
- 详见 §9.6 项目方使用须知

### 9.4 字段合并规则

项目 config 只填写差异字段，未填写的字段按通用默认；项目 config 中填写的字段会**完全覆盖**通用默认（不做数组追加），如需在默认基础上补充，请在 config 中显式列出全部值。

| 字段                  | 未填时回退到                                            |
| --------------------- | ------------------------------------------------------- |
| `project_name`        | 报告里用"通用基座"代替                                  |
| `default_mode`        | 主对话按 §2.4 自动判断                                  |
| `default_doc_paths`   | §2.1 默认路径                                           |
| `exclude_paths`       | 通用默认排除（`AGENTS.md` / `.bak` / `backup/` 等）     |
| `contracts`           | 不注入额外契约检查，视角 B 第 7 条只做通用语义检查      |
| `forbidden_apis`      | 不注入额外禁区检查                                      |
| `blindspot_checks`    | 不注入额外盲区检查点                                    |
| `performance_rules`   | 不注入额外性能红线                                      |
| `report_default_path` | `.local-review/report-{NNN}.md`（按 §2.2 序号取数规则） |
| `notes`               | 不追加任何项目说明                                      |

### 9.5 配置文件加载失败的处理

按以下优先级处理：

1. **文件不存在** → 静默回退到下一个来源（独立 config → `<project>-docs-cross-review` 兼容层 → 纯通用模式）
2. **YAML / JSON 解析失败** → 不要猜测，按通用模式执行；在报告"总评"里标注"项目 config 解析失败，本次未应用项目特化规则"
3. **字段类型错误**（如 `contracts` 写成字符串而不是数组）→ 跳过该字段，其他字段正常生效；在报告里列出被跳过的字段
4. **`schema_version` 缺失或不兼容** → 警告但不阻塞执行；缺失时按 §9.4 "未填字段"处理，不兼容时只识别能识别的字段，其余按 §9.4 处理

### 9.6 项目方使用须知（必读）

本 skill 通过 beehive 部署，skill 包内的 `configs/project-review-config.template.yaml` 已被 `beehive-skill.json` 的 `files` 字段锁定。**这意味着**：

- **项目方不能修改 `configs/project-review-config.template.yaml`**——任何修改都会被 beehive 判定为"修改了 skill"，需要回写源码仓库同步
- **配置应放在项目自己的目录**，推荐位置 `./configs/project-review-config.yaml`（项目根目录下）；也允许团队约定其他路径
- **模板文件仅作为 schema 与语法演示**，里面的示例值（`contracts` / `forbidden_apis` / `blindspot_checks` / `performance_rules` / `notes`）不是默认值
- **首次接入必做**：项目方第一次使用本 skill 时，应在自己的项目目录创建独立 config，按需填写真实项目特化信息，删除模板里所有示例内容

**判断你用的是模板还是独立 config 的方法**：

- 如果你看到路径里带 `.template.yaml` 后缀 → 这是模板，不能改
- 如果是项目根目录下的 `configs/project-review-config.yaml`（无 `.template` 后缀）→ 这是项目自己的 config，可以自由编辑

## 10. 重要约束

1. **review 和修改分离**：本 skill 只产出 review 报告，不自动修改被 review 的文档。修改由用户确认后再做。
2. **禁止推测当结论**：任一视角的结论都必须带当前模式下的有效证据（如检索命中、文件行号、引用资料、运行验证结果）。无法验证的标注"未验证假设"或"文档缺少证据"。
3. **不引入外部脚本**：本 skill 不引入 `context-scanner.js` 之类的脚本生成 `project-context.json`——Trae 原生的仓库检索 / 文件读取 / 文档读取能力已能当场验证，引入脚本会产生持久化产物违反"工具用完即留"原则，且产生规则双源。
4. **不引用 review 报告本身**：如果基于本 skill 的报告修改文档，修改时不要写"根据 review 报告第 X 条"——把结论内化到文档里。
5. **并行启动 subagent**：若当前环境支持并行 subagent，三个视角应尽量在单条消息里并行启动；若不支持，则按 §6 降级或串行执行。
6. **执行 review 时不改文件**：分配给任一视角的指令里都要明确写清"只做 review 产出，不要修改任何文件"。

## 11. 使用示例

### 示例 1：通用调用（无项目特化）

用户："帮我 review 一下架构设计文档"

主对话：

1. 确认 review 对象与报告路径（用户未指定路径 → 默认 `.local-review/report-001.md`，自动创建目录和 `.gitignore`）
2. 判断本次更适合 `repo-backed`、`doc-only` 还是 `mixed`
3. 判断是否降级
4. 用当前环境支持的并行 subagent 能力启动 3 个视角
5. 三个视角返回后，主对话汇总 + 对抗式交叉验证
6. 写报告到 `.local-review/report-001.md`
7. 暂停，等用户确认

### 示例 2：加载项目 config（推荐）

用户："帮我 review 一下这个 task-2026-07-27-001 元计划"

主对话：

1. 识别当前项目是否提供 docs review config；若有显式路径，优先加载
2. 若没有独立 config，再兼容读取现有 `<project>-docs-cross-review` skill 的 `## Project-Specific Config`
3. 把项目特化配置注入到三个视角的指令中
4. 后续步骤同示例 1

### 示例 3：降级为单视角

用户："快速过一下这个文档"

主对话：仅启动视角 A，报告总评里标注"降级为单视角 A"。
